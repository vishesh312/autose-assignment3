# Stage map

Source of truth: [`../DESIGN.md`](../DESIGN.md) (sections 2, 7, 8, 10, 14). In every stage the **orchestrator** (`autose`, deterministic Python) makes the pass/fail/route decision. LLM outputs (Judge ratings, Reviewer verdict) are inputs to that decision, not the decision itself. The only exception is the end of the pipeline, where a **human** decides to merge or close.

Run-wide limits that apply to every stage: $8 per run (the orchestrator aborts before a call that could exceed it), provider hard spend limit, 20 min timeout per agent subprocess, build job `timeout-minutes: 60`. Every stop writes `## Stop reason` into the failing stage's artifact, updates the status comment and applies a label.

## How each check is evaluated mechanically

**S1 Requirements.** The Analyst returns JSON constrained by `--json-schema`; the orchestrator re-validates it with the `spec` JSON Schema. It then checks in code that `acceptance_criteria` is non-empty and that each AC has non-empty `given`, `when`, `then` and `observable` fields. It sends only the AC list to the Judge (Haiku, no tools), whose `judge.json` must hold `testable: true` for every AC id. Finally it scans `open_questions` for `blocking: true`. The stage passes only if all predicates are true; a blocking question takes priority and ends the run in `needs-info`.

**S2 Design.** The orchestrator validates `design.json` against its schema, then for every entry in `changes`: checks that `path` exists in the checkout (or `new_file` is true), parses the file with Python's `ast` module and confirms the named `symbol` (e.g. `Query.between`) exists when `kind` is `modify`, and matches `path` against the allowlist `tinydb/**`, `tests/**`. It builds the AC-to-change map from each change's `acs` list and fails if any AC id from `spec.json` is uncovered.

**S3 Implementation.** After the Developer process exits, the orchestrator runs `git diff` against the base, fails on an empty diff, and matches every touched path against `tinydb/**` (anything else fails the check; files outside the design are only listed as a warning). "Builds" is defined as three commands all exiting 0: `python -m compileall -q tinydb`, `python -c "import tinydb"` and `mypy tinydb` (as in upstream CI).

**S4 Testing.** The orchestrator checks that the Tester changed only `tests/test_autose_issue_<N>.py`, runs `pytest --collect-only` and confirms every test id listed in `test_map.json` was collected and every AC has at least one. It then runs the full suite (`pytest`, with the upstream pycodestyle/coverage config) and requires exit code 0. For the anti-vacuous-test check it reverts the implementation files to the base commit, runs only the new test file, and requires at least one failure. Before each retry it compares the diff hash and the set of failing test ids with the previous attempt; if both repeat, it escalates without using up the remaining attempts.

**S5 Release.** No LLM is involved. The orchestrator force-pushes `autose/issue-<N>` with lease, opens or updates the PR with a body rendered from the artifacts by template, and posts the trace comment. It then checks that `gh pr view --json state` returns `OPEN`. Because pushes made with `GITHUB_TOKEN` do not trigger workflows, CI runs as a reusable workflow job on the head SHA and posts a commit status; the stage passes when that job concludes `success`.

**S6 Review.** The post-review job validates `review.json` against its schema and applies rules in code: `verdict: approve` requires `checks_performed` with at least one entry, and every finding must have non-empty `evidence` plus a `file` (and `line` where applicable). An invalid review is re-asked once, then treated as `changes_requested`. Routing is a fixed priority over finding categories (`approach` > `code` > `tests`), guarded by the `send_backs < 2` counter. The verdict is posted as a `COMMENT` review with the verdict in its header plus a label; merging is always left to a human.
