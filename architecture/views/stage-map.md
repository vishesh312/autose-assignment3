# Stage map

Source of truth: [`../DESIGN.md`](../DESIGN.md) (sections 2, **2.1 Complete routing table**, 7, 8, 10, 14) and the ADRs in [`../decisions/`](../decisions/). In every stage the **orchestrator** (`autose`, deterministic Python) makes the pass/fail/route decision. LLM outputs (Judge ratings, Reviewer verdict) are inputs to that decision, not the decision itself. The only exception is the end of the pipeline, where a **human** decides to merge or close.

Every failed check has exactly one route (DESIGN.md section 2.1). Attempt counters are per design: a new design, whether from the in-build design revisit or from an `approach` send-back, resets the Developer and Tester counters.

Where it runs: S1-S4 run in the build (or rework) job's **agent step**, offline and with **no GitHub token**, ending in a local commit; a *prepare* step (token) wrote the issue, trusted comments and branch facts to files beforehand. S5 runs in the **publish step** (token). S6 runs in the separate review job (prepare step with a read-only token, then a no-token agent step) and the post-review job. Every agent runs `claude -p --bare --restricted --strict-mcp-config`.

Run-wide limits that apply to every stage: $10 per run (the orchestrator aborts before a call whose cap could exceed it, and reserves one Reviewer cap before any rework; the review job gets the spend so far as a number, `spent_usd`) or a job timeout means **stop** with `autose:failed` and the reason in the stage artifact. Also: provider hard spend limit, 20 min timeout per agent subprocess, job `timeout-minutes` build/rework 60, review 45, CI 15; no new agent call starts if less than the 20 min call timeout + 2 min of the job remains. Every stop writes `## Stop reason` into the failing stage's artifact, updates the status comment and applies a label.

## How each check is evaluated mechanically

**S1 Requirements.** The Analyst returns JSON constrained by `--json-schema`; the orchestrator re-validates it with the `spec` JSON Schema. It then checks in code that `acceptance_criteria` is non-empty and that each AC has non-empty `given`, `when`, `then` and `observable` fields. It sends only the AC list to the Judge (Haiku, no tools), whose `judge.json` must hold `testable: true` for every AC id. Finally it scans `open_questions` for `blocking: true`. The stage passes only if all predicates are true. A blocking question ends the run in `needs-info`; any other failure feeds the reasons back to a second Analyst attempt.

**S2 Design.** The orchestrator validates `design.json` against its schema, then for every entry in `changes`: checks that `path` exists in the checkout (or `new_file` is true), parses the file with Python's `ast` module and confirms the named `symbol` (e.g. `Query.between`) exists when `kind` is `modify`, and matches `path` against the allowlist `tinydb/**`. It builds the AC-to-change map from each change's `acs` list and fails if any AC id from `spec.json` is uncovered. The checker output is the retry input for the second attempt.

**S3 Implementation.** After the Developer process exits, the orchestrator runs `git diff` against the base, fails on an empty diff, and matches every touched path against `tinydb/**` (anything else fails the check; files outside the design are only listed as a warning). "Builds" is defined as three commands all exiting 0: `python -m compileall -q tinydb`, `python -c "import tinydb"` and `mypy tinydb` (as in upstream CI). Each failure uses one Developer attempt; before retrying, the orchestrator compares the diff hash and failing test set with the previous attempt, and if either repeats it escalates to the design revisit at once.

**S4 Testing.** The check has two parts with separate counters. *Tester's own check:* the orchestrator confirms the Tester changed only `tests/test_autose_issue_<N>.py`, runs `pytest --collect-only` and checks that every test id in `test_map.json` was collected and every AC has at least one, and runs the new test file with the implementation files reverted to the base commit, requiring at least one failure (anti-vacuous-test check). A failure here goes back to the Tester. *Suite:* it runs the full suite (`pytest` with the repo `pytest.ini`) and `mypy tinydb tests`, and requires exit code 0 from both; check subprocesses get a scrubbed environment and git runs with hooks and fsmonitor disabled; a failure goes back to the Developer with the failing ids and output. The orchestrator then renders `test_report.md` from pytest's JSON/junit results, `test_map.json` and the fails-on-base results, so the report does not come from the agent that wrote the tests.

**S5 Release.** No LLM is involved, and this is the first point where a token is present again: the agent step has only made a local commit, and the publish step takes over. It first runs the final path gate, `git diff --name-only --no-renames <base> HEAD`, and stops if any path is outside the allowlist (this also closes an index-staging bypass of the per-attempt check). Only then are push credentials configured; it force-pushes `autose/issue-<N>` with lease, opens or updates the PR (always `gh --repo vishesh312/tinydb`) with a body rendered from the artifacts by template, and posts the trace comment, labels and status; a failing `gh`/`git` call is retried once after 10 s. It then checks that `gh pr view --json state` returns `OPEN`. Because pushes made with `GITHUB_TOKEN` do not trigger workflows, CI runs as a reusable workflow job on the head SHA and posts a commit status; the stage passes when that job concludes `success`, and a CI failure stops the run with the CI log linked in `pr.md`.

**S6 Review.** The review job's prepare step (read-only token) writes the issue text, trusted comments and `git diff base...head` to files; the agent step (no token) reads only those, the PR head checkout and its own previous `review.json` (`autose-issue<N>-review-r<k>`), and receives the run's spend so far as a number (`spent_usd`). The post-review job validates `review.json` against its schema and applies rules in code: `verdict: approve` requires `checks_performed` with at least one entry and no `blocking` finding, `changes_requested` requires at least one `blocking` finding, and every finding must have non-empty `evidence` with a `file:line` reference. It first discards a review whose SHA is no longer the PR head. An invalid review is re-asked once, but only if `spent_usd` plus one Reviewer cap still fits the run cap; a review that stays invalid is posted under "INVALID REVIEW (not an approval)" and the run ends `awaiting-human`, since it has no category to route on. Only `blocking` findings route; routing is a fixed priority over their categories (`approach` > `code` > `tests`), guarded by the `send_backs < 2` counter and by the reservation rule (the rework starts only if one Reviewer cap still fits under the $10 cap after it). The verdict is posted as a `COMMENT` review with the verdict in its header plus a label; merging is always left to a human.
