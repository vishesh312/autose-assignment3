# ADR-013: At most two send-backs, then one final review; verdict posted as a COMMENT review plus a label; never merge

- Status: Proposed (2026-11-24). This records our interpretation of the brief (DESIGN §13) and stays Proposed until the course staff or our runs give us a reason to confirm or change it.
- Decision area: D2 Control flow and D8 Reviewer independence (stage 6 semantics; not a numbered D in the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

Stage 6 of the brief says: "Requested changes go back to the stage that needs fixing, at most twice", with the check "The reviewer approves, or two review rounds are used up." It also says "the workflow ends after the review, and a person decides whether to merge". Three things are left open:

1. **What a "round" is.** "At most twice" can mean two reviews in total (so only one send-back can ever be acted on) or two send-backs (so up to three reviews). If the second review requests changes in the first reading, the human gets code with known blocking findings and nobody checks whether they were real.
2. **How "approve" is expressed on GitHub.** The PR is opened by deterministic code with the job's `GITHUB_TOKEN` (ADR-005), so its author is `github-actions[bot]`. GitHub does not let a PR's author approve or request changes on their own PR, and the reviewer job deliberately has no token at all (ADR-008). Creating PRs with `GITHUB_TOKEN` also requires the repository setting "Allow GitHub Actions to create and approve pull requests", which we enable; it still does not allow self-approval.
3. **Where requested changes go.** The brief's diagram routes "approach issue" to Design and "code issue" to Implementation. Our reviewer can also find that the *tests* are wrong (vacuous or missing an AC), which is neither.

## Decision

### Rounds

- A **send-back** is a reviewer verdict of `changes_requested` that the orchestrator acts on by rerunning stages. We allow **at most 2 send-backs per run**, so there are up to **3 reviews**:

```
round1: ci → review#1 ─ approve ─────────────────────────────▶ finalize (awaiting human)
                     └ changes → send-back 1 ─▶ round2: rework → ci → review#2 ─ approve ─▶ finalize
                                                                             └ changes → send-back 2 ─▶ round3: rework → ci → review#3 (final) ─▶ finalize
```

- **Review #3 is final and non-routing.** It is a full review with the same prompt and evidence rules (ADR-008); its verdict is posted and labelled, but the orchestrator does not act on it. This keeps the guarantee that **no unreviewed code reaches the human**: every head SHA the human is asked to merge has a posted review of that exact SHA.
- A rework is skipped if the run budget cannot also pay for the review after it (ADR-006 reservation); the last posted review then stands.
- In the workflow these are the jobs `round1`, `round2`, `round3` (calls to `autose-round.yml`) with `if:` conditions on the previous round's `verdict` output (ADR-002), because Actions jobs cannot loop.

### Routing

Only `blocking` findings route (ADR-008). Highest-impact category wins, and the pipeline then reruns every later stage:

| Highest blocking category | Rerun from | Why this stage |
|---|---|---|
| `approach` | S2 Design (Architect receives the `approach` findings) | The plan is wrong; fixing code alone would only implement the wrong plan again |
| `code` | S3 Implementation (Developer receives the `code` findings) | The plan is fine, the code is not |
| `tests` | S4 Testing (Tester receives the `tests` findings) | Code may be right but tests do not show it |

"Highest wins" because an earlier stage's rerun includes the later ones: fixing the approach regenerates code and tests, so lower-category findings are addressed in the same pass. The rework then runs S5 (force-push with lease, update the same PR) and CI before the next review. Findings are passed as data in schema fields only, never the reviewer's reasoning (ADR-003); the rework's agents still never see the raw issue.

An invalid review (still invalid after one re-ask) is recorded as `changes_requested` with an "invalid review" note, so it can never count as approval; since it has no categorised blocking finding it cannot route, and the run ends `awaiting-human`.

### How the verdict is published

- The tokenless review job uploads `review.json`; a separate `post-review` job (`pull-requests: write`, `issues: write`) renders `review.md` and posts it as a PR review with event **`COMMENT`**. The first line is a verdict header: `AutoSE review (round k/3): APPROVE` or `... REQUEST_CHANGES`, followed by findings with `file:line` and evidence.
- It sets exactly one of the labels `autose:review-approved` / `autose:review-changes-requested` (removing the other), and after the final round `autose:awaiting-human`.
- The sticky status comment on the issue links each review.

### Never merge

No job calls a merge API or enables auto-merge; `main` is branch-protected, so even a bug in our code could not push there. The workflow ends at `finalize`; a human merges or closes.

## Alternatives considered

1. **Two reviews in total** (send-back after review #1 only; review #2 is final). Cheaper by one rework and one review (~$2.40, ADR-006). Rejected as the default because "requested changes go back ... at most twice" reads most naturally as two send-backs, and because it acts on only one round of feedback. It is a configuration change (max send-backs = 1) if the course staff read the brief this way.
2. **Two send-backs and no review after the second** (the human gets the rework from send-back 2 unreviewed). Saves one Opus call. Rejected: the human would be shown code whose last review referred to a different SHA, which defeats the point of stage 6.
3. **Posting as `APPROVE` / `REQUEST_CHANGES` with a second identity** (a PAT or a GitHub App for the reviewer). Gives native review states and could satisfy a "required approvals" rule. Rejected: a second long-lived credential (ADR-009), and a bot approval could count towards branch protection's required reviews, which would weaken the human gate. A COMMENT review cannot satisfy a required-approval rule, which is what we want.
4. **Route to the earliest stage any finding names, regardless of severity.** Rejected: one minor wording note on a test would send the run back, which is the over-strict reviewer failure ADR-008 guards against.

## Consequences

- **Positive.** Every head SHA shown to the human has a posted review of that SHA. The worst case is bounded: 3 reviews and 2 reworks, and never more than the $8 run cap. Labels let a maintainer filter PRs by verdict. A bot verdict cannot satisfy branch protection.
- **Negative.** GitHub's UI shows the review as "commented", not "approved"; readers must read the header or label. A full three-round run costs about 2.7x a happy-path run (~$7.6 by ADR-006's estimates). With the $8 cap and the review reservation, ADR-006's numbers suggest the second send-back will often be unaffordable, so in practice the cap, not this ADR, may limit runs to one send-back; the ledger will show how often. The final review may request changes the pipeline will not act on; the PR then reaches the human with known open findings, clearly labelled.
- **Risks.** The interpretation may not match the markers'; switching to alternative 1 is a single setting. "Highest wins" can over-correct: an `approach` finding reruns design even if most findings were small `code` issues.

## Answers to the brief's questions

- **What does "at most twice" mean here?** At most two send-backs, then one final non-routing review, so the stage-6 check "reviewer approves, or two review rounds are used up" is always followed by a review of the final code.
- **Where do requested changes go?** `approach` → S2, `code` → S3, `tests` → S4, highest wins, then forward through S5 and CI to review.
- **Who makes the final decision?** A human. We never merge; our approval is advisory and cannot satisfy branch protection.

## How we will know if this is wrong

- If, across our runs, review #3 almost never differs from review #2 (same findings, same verdict), the third review adds cost without information and alternative 1 is better.
- If send-backs to S2 routinely regenerate a near-identical design (same `changes` list), "highest wins" is over-correcting and we route on the majority category instead.
- If E1 shows variant A requesting changes on correct PRs, two send-backs mostly burn budget, and the cap should drop to one.
- If course staff confirm a different reading of "two review rounds", we supersede this ADR.
