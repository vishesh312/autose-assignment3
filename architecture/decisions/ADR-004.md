# ADR-004: State lives in the job directory, workflow artifacts, the branch, and GitHub records; re-triggers start fresh

- Status: Accepted (2026-11-24)
- Decision area: D4 State (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

The pipeline has state at four scopes: within a stage loop (attempt counters, last diff hash), between jobs of one run (build → CI → review → rework), between runs for the same issue (a maintainer answers clarifying questions, or comments `/autose` again), and for humans after the run (what happened and why).

GitHub Actions facts that constrain the options:
- Each job on a hosted runner starts on a fresh VM, so the filesystem does not survive between jobs.
- Workflow artifacts (`actions/upload-artifact` v4) are scoped to a run, immutable per name unless `overwrite: true`, and kept for 90 days by default (configurable down, not beyond repo/org limits).
- The Actions cache is keyed best-effort and can be evicted at any time (10 GB per repo with LRU eviction). It is for speed, not for correctness.
- Re-running a failed job reuses outputs and artifacts from jobs that already succeeded in the same run.
- The reviewer job must not see the builders' artifacts (ADR-003, ADR-008).

## Decision

| Scope | Store | Content |
|---|---|---|
| Inside a job | `$AUTOSE_HOME/issue-<N>/` on the runner | Artifacts, `state.json` (stage, attempts, `send_backs`, `cost_usd`, `base_sha`, `head_sha`, status), `ledger.jsonl` |
| Between jobs in one run | Workflow artifact `autose-issue<N>-r<round>` + job outputs (`verdict`, `head_sha`, `pr`, `route`) | Everything the next build-side job needs. The review job downloads **none** of it; the only artifact it downloads is its own previous round's `review.json` (`autose-issue<N>-review-r<k>`, by exact name), plus the inputs listed in ADR-003 |
| Code | Branch `autose/issue-<N>` | The diff the human will merge; nothing else is committed |
| Human-visible, durable | Sticky status comment on the issue (`<!-- autose:status -->`, edited in place); PR body (`pr.md`); one PR trace comment with `spec.md`/`design.md`/`test_report.md` in collapsed sections; the PR review (`review.md`) | Survives the 90-day artifact retention; is the audit trail for graders and maintainers |
| Between runs | Issue thread (Q&A), labels (`autose:needs-info`, `autose:failed`, `autose:awaiting-human`, review-verdict labels), existing branch and PR | Enough to resume the human conversation, not the machine state |

**Restart semantics.** A re-trigger (label or `/autose` on the issue) starts a **fresh pipeline**: it reads the issue thread again (so answered questions now count), resets `autose/issue-<N>` from `main`, force-pushes with lease, and **updates** the existing PR rather than opening a second one. It does not try to resume at the stage where the previous run stopped. Re-running a *failed job* inside the same Actions run is different: it picks up the artifacts of the jobs before it, so a review job that timed out can be re-run without rebuilding. Upload steps use `overwrite: true` so a re-run job can replace its own artifact.

**Not used:** committing artifacts to the branch, and the Actions cache.

## Alternatives considered

1. **Artifacts committed to the branch** (e.g. `.autose/issue-<N>/spec.md`). Durable, versioned with the code, and visible in the PR. Rejected: the reviewer checks out the PR head, so it would see `spec.md`, `design.md` and `test_report.md` in its working tree, which breaks independence (ADR-008); they would also land in `main` on merge unless someone deletes them; and every artifact change becomes a commit that adds noise to the diff the reviewer and human must read.
2. **PR/issue comments as the machine state** (parse the last state comment on resume). Durable and visible, and would allow resuming mid-pipeline across runs. Rejected as the *primary* store: comments are editable by anyone with write access, are size-limited (65,536 characters per body), and parsing state back out of Markdown is fragile. We still write comments, but as a one-way projection of state for humans.
3. **Actions cache as cross-run state.** Fast and needs no extra API. Rejected: eviction is not under our control, and a cache miss would silently change behaviour.
4. **External store (S3, a database, a gist).** Full control over retention and resume. Rejected: another secret and another service for a system whose runs are short and whose durable record is already on GitHub.
5. **Resume from last successful stage across runs.** Saves tokens when a run dies late. Rejected for now: the issue may have changed between runs (that is often why the maintainer re-triggers), and a stale spec carried into a new run is a worse failure than paying for stage 1 again.

## Consequences

Positive:
- The reviewer's independence is enforced by *where state is*, not only by prompts: its checkout contains the code, and nothing else of ours.
- The branch contains only the change a human would merge.
- A run is fully reconstructable after artifact expiry from the issue status comment, PR body, trace comment and review.
- Restart is simple and idempotent: same branch name, same PR, force-with-lease, status comment edited in place.

Negative:
- A re-trigger repeats every stage, including ones that passed. For tinydb this is affordable (the suite takes under 1 s; cost is dominated by model calls, bounded by the $10 cap), but it is waste.
- Force-pushing the branch discards the previous attempt's commits. Earlier diffs survive only as `diff.patch` in workflow artifacts (90 days) and in PR history.
- Workflow artifacts expire; the raw `ledger.jsonl` must be copied into `results/` in the submission repo for the report, or it is lost.

Risks:
- A human pushing to `autose/issue-<N>` between runs could have their commits overwritten, because `--force-with-lease` only protects against races inside a run (a fresh run fetches before resetting). Mitigated: before resetting the branch, the orchestrator in the build/rework job checks for commits the bot did not author and, if there are any, stops with a message instead of force-pushing (DESIGN §10, ADR-010). We still document that the branch belongs to the bot.
- If two jobs in a run upload the same artifact name without `overwrite`, the second fails; we name artifacts per round to avoid this.

## Answers to the brief's questions

- **Where is information stored between stages?** On the runner inside a job; in per-round workflow artifacts and job outputs between jobs; the code on `autose/issue-<N>`.
- **Between runs?** In the issue thread, labels, the branch and the PR; durable human-facing copies in comments and the review.
- **What happens if a run is restarted?** A new trigger starts a fresh pipeline, re-reads the thread, resets the branch from `main` and updates the same PR. Re-running a failed job within a run reuses the artifacts of the jobs before it.
- **Beyond the brief:** state placement is also an independence mechanism (nothing of ours on the branch), and the human-visible record is designed to outlive artifact retention.

## How we will know if this is wrong

- If many re-triggers fail at the same late stage after redoing early stages identically (visible as identical `spec.json` hashes across runs in the ledger), resuming is worth its complexity.
- If a review ever cites `spec.md`, `design.md` or `test_report.md` content it should not have, state is leaking into the review job and this ADR (and ADR-008) must change.
- If artifacts are missing when a job re-runs, our re-run assumption is wrong for the reusable-workflow layout and we must pass more state through job outputs.
