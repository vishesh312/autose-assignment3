# ADR-001: Five agents split at trust boundaries, with Release as plain code

- Status: Accepted (2026-11-24)
- Decision area: D1 Splitting the work (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

The brief fixes six stages (Requirements, Design, Implementation, Testing, Release, Review), each with an artifact and a check, and requires a reviewer that is independent of the other agents. It leaves open how many agents carry out those stages.

Facts about this system that shape the split:

- The target is tinydb @ `edff96a` (ADR-012). The suite has 228 tests and runs in under 1 s, so the expensive part of every stage is the model call, not the checks.
- Issue text is untrusted. Any agent that reads it and can also write to the working tree is a place where injected instructions can turn into code.
- Stages 3 and 4 form a loop (failing tests go back to implementation). If one context writes both the code and the tests that grade it, the stage-4 check measures the agent's consistency with itself, not with the spec.
- Stage 5 (push the branch, open or update the PR, wait for CI) needs no judgement, but it is the only stage that needs `contents: write` and `pull-requests: write`.
- Every extra agent adds a hand-off (ADR-003), a schema, a prompt to maintain and per-call overhead. In our harness (ADR-011) each agent invocation re-reads the files it needs, so splitting has a real token cost.

## Decision

We use **five agents and one single-shot LLM judge**. Stages that need no judgement have no agent.

| Stage | Executed by | Why it is its own unit |
|---|---|---|
| 1 Requirements | **Analyst** (A1 `requirements-spec` skill + issue adapter), read-only | The only agent that acts on raw issue text, so it gets no write tools (principle 6) |
| 1 check | **Judge** (one Haiku call, no tools, no loop) | The spec author must not rate its own ACs as testable (principle 1) |
| 2 Design | **Architect**, read-only, sees `ARCHITECTURE.md` | Different context: architecture knowledge, no raw issue; its output is checked by an AST-based checker (ADR-007) |
| 3 Implementation | **Developer**, writes only `tinydb/**` | Needs write access; must not see the raw issue |
| 4 Testing | **Tester**, writes only `tests/test_autose_issue_<N>.py` | Tests are the Developer's grader, so they come from a separate context built from the ACs, not from the implementer's beliefs |
| 5 Release | **Deterministic code** (`gh`, git) | No judgement needed; keeps GitHub write tokens out of every agent process (ADR-005) |
| 6 Review | **Reviewer**, separate job, different model, no push | Required by the brief; independence is detailed in ADR-008 |

The rule we apply is principle 3 of DESIGN.md: **split at trust boundaries, not at stage boundaries.** A new agent is justified only if the role needs a different context, different permissions, or independence from another role. Stages 1 and 2 could share a context on capability grounds, but they differ in trust (the Analyst reads raw issue text; the Architect must not) and the Architect's output is checked against the Analyst's, so we keep them apart.

## Alternatives considered

1. **One agent for all six stages** (the shape of most "fix this issue" actions). One long context is cheap in hand-offs and keeps full continuity of reasoning. Rejected because: (a) the agent would grade its own homework at stages 1, 2 and 4 (it writes the code and the tests that judge it, which is exactly the vacuous-test failure our fails-on-base check exists to catch); (b) it would need raw issue text *and* write access *and* GitHub access in one process, so a single injection reaches everything; (c) a reviewer that is the same agent cannot be independent, so we would need a second agent anyway.
2. **One agent per stage (six agents, including a Release agent).** Rejected for Release: an LLM that runs `git push` and `gh pr create` adds non-determinism and needs a write token in its environment, for no benefit, since the PR body is a template over existing artifacts. For the other five stages this alternative is what we chose, minus the Release agent.
3. **A combined "Builder" for stages 3 and 4** (implements and writes its own tests in one context, as human developers often do). This is the strongest rival: it removes a hand-off, lets tests evolve with the code, and avoids Developer/Tester disputes. We reject it provisionally because it collapses the only independent check on implementation before review. Because the trade-off is genuinely uncertain, we test it in **E2**.
4. **A planner agent that decides which stage to run next** (orchestrator-worker with an LLM orchestrator). Rejected in ADR-002: control flow is owned by code.

## Consequences

Positive:
- Each artifact has a checker other than its author: Judge for the spec, AST checker for the design, Tester's tests plus the suite for the code, fails-on-base for the tests, Reviewer and then a human for everything.
- Write-capable agents (Developer, Tester) never see raw issue text; read-only agents that see it cannot write. An injection in the issue must survive the Analyst's distillation into a schema before it can influence code.
- Each agent has a short, specific prompt and schema, which keeps failures diagnosable: the ledger records which agent failed which check.

Negative:
- More hand-offs: each must be designed and can lose information (ADR-003). The Developer cannot ask the Analyst what an AC meant.
- More calls and re-reading of the repo. We expect a full run to cost noticeably more tokens than a single-agent run; the $8 run cap (ADR-009) bounds it.
- Developer/Tester disagreement becomes a new failure mode. We handle it with a *contest* field in `dev_notes.json` and one Tester re-check per contested test.

Risks:
- The Tester sees the implementation in the repo (it needs it to import and run code), so it can still be pulled toward what the code does rather than what the ACs say. The fails-on-base check catches tests that pass trivially, but not tests that encode a wrong behaviour that the implementation also has.
- Splitting does not by itself create diversity: four of the five agents use the same model (ADR-006). Independence of the Tester comes from context, not from a different model.

## Answers to the brief's questions

- **How many agents, and which stages does each handle?** Five agents (Analyst S1, Architect S2, Developer S3, Tester S4, Reviewer S6) plus a single-call Judge used inside the S1 check. S5 and all routing are deterministic code.
- **Why better than one agent for everything?** One agent would grade its own spec, design and tests, would hold raw issue text and write access at once, and could not be the independent reviewer the brief requires.
- **Why better than one agent per stage?** We are one agent per stage except for Release, where an agent adds cost and risk and nothing else. We would also merge stages if two roles needed the same context and the same permissions; none of ours do.
- **Beyond the brief:** the split is tied to permissions (ADR-005), to what each agent may see (ADR-003), and to which checks are possible (ADR-007). The Developer/Tester split, the most debatable part, is the subject of experiment E2.

## How we will know if this is wrong

- **E2** (single Builder vs Developer + Tester, same frozen `spec.md`/`design.md`, 5 issues, local runs). If the Builder variant matches or beats the split on hidden-test pass rate and fails-on-base rate, at clearly lower token cost, we supersede this ADR and merge stages 3–4 into one agent.
- If across real runs the Tester's tests rarely fail on base or rarely catch anything the suite does not, the separate Tester is not earning its cost.
- If the Developer/Tester contest path fires on a large share of runs, the hand-off between them is too lossy and the split boundary is in the wrong place.
- If stage-1 Judge and Analyst disagree almost never, or the Judge rejects ACs that the hidden tests show were testable, the Judge is either redundant or miscalibrated.
