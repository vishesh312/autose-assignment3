# ADR-007: Deterministic checks decide every stage; one LLM judge at stage 1; the orchestrator decides, a human merges

- Status: Accepted (2026-11-24)
- Decision area: D7 Checks (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

The brief fixes one check per stage: all ACs testable (S1), the plan names files and functions (S2), the code builds (S3), all new and existing tests pass (S4), the PR is open and CI passes (S5), the reviewer approves or two rounds are used up (S6). It leaves open *how* each check is done and *who* decides.

Forces specific to this system:

- **Agents are optimistic about their own work.** An agent asked "did you finish?" usually says yes. Principle 1 of DESIGN.md: no agent grades its own homework.
- **Most checks can be code.** tinydb is pure Python with type hints and a 228-test suite that runs in under 1 s (ADR-012), so running the whole suite, `mypy` and an AST lookup after every attempt is cheap. An LLM call is slower, costs money and can be argued with by the text it reads.
- **Some checks are semantic.** "Is this AC testable?" cannot be fully decided by a parser, and "does this PR solve the issue?" is the reviewer's job (ADR-008).
- **Principle 2:** LLMs produce artifacts, code decides transitions. Every agent returns JSON (`--json-schema`, ADR-003), so checks can read fields instead of parsing prose.
- **Vacuous tests are the known failure of agent-written tests**: a test that passes before and after the change proves nothing.

## Decision

Every check is a predicate evaluated by the `autose` orchestrator (ADR-002). LLM outputs are *inputs* to some predicates; no LLM ever decides a transition by itself.

| Stage | Deterministic predicates | LLM input | On failure |
|---|---|---|---|
| 1 Requirements | `spec.json` valid against schema; ≥1 AC; every AC has non-empty given/when/then/observable; no `blocking` open question | Judge (Haiku 5.5, one call, sees only the AC list) returns `testable` per AC with a reason | Blocking question: post questions, label `autose:needs-info`, stop (correct outcome for the vague issue). Untestable AC: one Analyst retry with the judge's reasons, then stop |
| 2 Design | `design.json` valid; ≥1 change; every `path` exists or is `new`; every `symbol` with `kind: modify` exists in that file (AST lookup); every AC maps to ≥1 change; paths only under `tinydb/**`, `tests/**` | – | One Architect retry with the checker's message, then stop |
| 3 Implementation | diff non-empty; every touched path matches `tinydb/**`; `python -m compileall -q tinydb`; `python -c "import tinydb"`; `mypy tinydb` | – | Counts as a failed Developer attempt (attempt budget in ADR-009) |
| 4 Testing | Tester touched only `tests/test_autose_issue_<N>.py`; every AC maps to ≥1 collected test id (`pytest --collect-only`); full suite passes; ≥1 new test **fails on base** (implementation files reverted to `base_sha`) | – | Back to S3 with failing ids and assertion text (≤4 KB); after 3 Developer attempts, back to S2 once; then stop. Same diff hash or same failing set as last attempt: escalate immediately |
| 5 Release | `gh pr view` reports `OPEN`; CI reusable workflow on the head SHA concludes `success` (commit status) | – | Stop with reason; CI is the same suite S4 ran, so a failure here means an environment difference, not something an agent should guess at |
| 6 Review | `review.json` valid; `approve` needs ≥1 entry in `checks_performed`; every finding has `file:line` and evidence; `changes_requested` needs ≥1 `blocking` finding | Reviewer verdict and finding categories (Opus 5.5) | Invalid review re-asked once. Verdict routes the work (ADR-013); a **human** merges or closes |

Notes on specific checks:

- **"Builds" includes mypy.** Python has no compile step, so `compileall` alone only catches syntax errors. Upstream tinydb's CI runs mypy (`pytest --mypy -m mypy tinydb tests`), the package ships `py.typed` and its own mypy plugin (`mypy.ini` loads `tinydb/mypy_plugin.py`), so a change that breaks typing would fail upstream CI. Including it in S3 moves that failure to the cheapest place to fix it.
- **Fails-on-base is the anti-vacuous-test check.** The orchestrator stashes the Developer's changes to `tinydb/**`, keeps the new test file, runs only the new tests, and requires at least one to fail; then restores. This is what turns "tests pass" from a statement about the Tester's consistency into a statement about the change.
- **Code checks the Judge's structure, the Judge checks meaning.** The schema guarantees every AC *has* an observable; the Judge rates whether that observable can be asserted in a test. The Judge never sees the issue or the Analyst's reasoning, so it cannot be persuaded by them.
- **S2 has no LLM judge.** The brief's check is structural (files and functions named), and an AST lookup verifies it exactly, including catching invented symbols. Whether the design is *good* is tested downstream by S3–S4 and by the reviewer, who can route `approach` findings back to S2.
- **Contested tests.** The Developer may list a test in `dev_notes.json.contested_tests`; the Tester re-checks it against the spec once. The Developer can never edit tests (path allowlist), so a dispute cannot be "resolved" by deleting the test.

## Alternatives considered

1. **An LLM judge at every stage** ("is this design good?", "does this code look right?"). Gives a richer signal on design quality. Rejected: it adds five LLM calls per pass, each of which can be swayed by confident artifact prose, and it duplicates the reviewer. For S2–S5 the brief's checks are mechanically decidable, so an LLM would only add noise to a decision code can make exactly.
2. **Let each agent report its own pass/fail** (e.g. the Developer's `self_check` field decides S3). Cheapest. Rejected by principle 1: `self_check` is kept as information for the human, never as a gate.
3. **Only the brief's literal checks** (suite passes, no fails-on-base, no AC→test mapping, no mypy). Simpler. Rejected because a Tester can satisfy "all tests pass" with tests that assert nothing about the change, and a Developer can satisfy "builds" with a type error. Those are the two most likely silent failures on this repo.
4. **Run hidden acceptance tests as a check.** Rejected: they are our evaluation instrument (brief, Part 1). Using them as a gate would leak the answer and invalidate the results section.

## Consequences

- **Positive.** Every transition is reproducible from `ledger.jsonl`: the same artifacts give the same decision. Checks are fast (seconds) and free. The fails-on-base and AC→test predicates make the stage-4 check meaningful. Failures carry a precise reason into the next attempt.
- **Negative.** Structural checks can be satisfied by structurally correct but wrong artifacts: a design that names real functions but the wrong ones passes S2. We rely on S4 and the reviewer to catch that, which costs a loop.
- **Risks.** Fails-on-base is weak for features: if the new tests import a symbol that does not exist on base, every test "fails" with an `ImportError` or `AttributeError`, so the check passes even if the assertions are trivial. It reliably catches fully vacuous tests and is strongest for bug fixes. The reviewer is told to look for weak assertions (ADR-008). The Judge can be wrong in either direction; a false "untestable" costs one retry, a false "testable" surfaces at S4 when no meaningful test can be written.

## Answers to the brief's questions

- **How is each check carried out?** By the table above: deterministic predicates (schema, AST, path allowlists, compileall/import/mypy, pytest with collect-only coverage and fails-on-base, PR state and CI status) at all six stages, plus one Haiku judge at S1 and the Opus reviewer at S6.
- **Who makes the final pass or fail decision?** For S1–S5, the orchestrator, as the AND of the predicates; no agent can override it. For S6, the reviewer's verdict (validated by the orchestrator's evidence rules) decides whether work is routed back. The final decision on the change is a **human's**: the workflow never merges (ADR-013), and `main` is branch-protected.
- **Beyond the brief.** Checks run on every attempt, not once; failure output is truncated and passed forward as facts only (ADR-003); the no-progress detector turns repeated identical failures into an immediate stop instead of burning budget (ADR-009).

## How we will know if this is wrong

- **Hidden tests vs our checks.** If PRs that pass S4 (including fails-on-base) fail the hidden acceptance tests often, our checks are measuring the wrong thing; we would add per-AC fails-on-base or mutation testing.
- **E2** (ADR-001): if the single-Builder variant has the same hidden-test pass rate and the same rate of AC tests contradicted by hidden tests, the Tester's independence is not adding value to the S4 check.
- If the reviewer frequently files `approach` findings on designs that passed S2, the S2 check is too weak and an LLM design check may be worth its cost.
- If S5 CI ever fails after S4 passed, our local check environment differs from CI and must be aligned.
