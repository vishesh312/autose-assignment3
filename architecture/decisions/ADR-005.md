# ADR-005: Built-in harness tools per agent, no MCP, GitHub only through `gh` in deterministic code

- Status: Accepted (2026-11-24). Mechanism amended by [ADR-014](ADR-014.md): with the default Codex backend, per-agent `--tools`/Bash allowlists are replaced by the Codex OS sandbox (`read-only` / `workspace-write`, network off); the no-MCP, no-GitHub-for-agents and post-run path-check decisions are unchanged.
- Decision area: D5 Tools (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

Agents need to read the repository, some need to edit files, and some need to run code (tests, mypy, scratch probes). Some stages need GitHub: pushing the branch, opening the PR, posting comments and the review, applying labels. Options for providing GitHub access include the GitHub MCP server, the `gh` CLI and the REST API, each usable either *by an agent* or *by our code*.

Constraints specific to this system:
- Issue text is untrusted, and the PR branch is produced from it. A write-capable agent with a GitHub tool could be steered into commenting, labelling, pushing elsewhere or closing issues.
- `actions/checkout` persists the job token into `.git/config` unless `persist-credentials: false`. Any agent with Bash in that checkout could read it or `git push` with it.
- `GITHUB_TOKEN` permissions are set per job; a token can never be narrower than its job.
- Claude Code (ADR-011) separates `--tools` (which built-in tools exist at all) from `--allowedTools` (which are auto-approved, including `Bash(<prefix>)` rules). In `-p` mode a tool call that is not approved is denied, not prompted.
- The brief: "Give each job only the permissions it needs."

## Decision

**Least privilege in three layers** (DESIGN.md principle 5), plus a post-run check:

1. **Job token permissions.** gate: `issues: write`, `pull-requests: read`, `contents: read`. build/rework: `contents: write`, `pull-requests: write`, `issues: write`. ci: `contents: read`, `statuses: write`. review: `contents: read`, `issues: read`, `pull-requests: read`; a *prepare* step uses the token to write the issue text, trusted comments and `git diff` to files, and the *agent* step then runs with no token in its environment. post-review: `pull-requests: write`, `issues: write`. finalize: `issues: write`, `pull-requests: write`. The workflow-level default is `permissions: {}`.
2. **Process environment.** Agent subprocesses never receive `GH_TOKEN`/`GITHUB_TOKEN`; the orchestrator builds an explicit environment for them containing only what the CLI needs (`ANTHROPIC_API_KEY`, `PATH`, `HOME`, Python variables). Every checkout uses `persist-credentials: false`; the build job adds credentials only for the push step, after all agents have finished.
3. **Agent tool allowlist** via `--tools` / `--allowedTools`, with `--bare` so the PR branch cannot add tools, hooks, MCP servers or `CLAUDE.md` instructions:

| Agent | `--tools` | Bash auto-approved (`--allowedTools` rules) | May write |
|---|---|---|---|
| Analyst | Read, Grep, Glob | none | nothing (orchestrator renders output) |
| Architect | Read, Grep, Glob | none | nothing |
| Developer | Read, Grep, Glob, Edit, Write, Bash | `Bash(python -m pytest *)`, `Bash(python -m mypy *)`, `Bash(python -m compileall *)`, `Bash(git diff *)`, `Bash(git status *)` | `tinydb/**` |
| Tester | Read, Grep, Glob, Edit, Write, Bash | `Bash(python -m pytest *)` | `tests/test_autose_issue_<N>.py` |
| Reviewer | Read, Grep, Glob, Write, Bash | `Bash(python -m pytest *)`, `Bash(python <probe-dir>/*)` (scratch probes only), `Bash(git diff *)`, `Bash(git log *)`, `Bash(git show *)` | `$RUNNER_TEMP/review-probes/` (`--add-dir`) |

No agent gets MCP, WebFetch, WebSearch or any GitHub tool.

4. **Post-run path allowlist.** After each write-capable agent exits, the orchestrator runs `git status --porcelain` and fails the stage if any changed path is outside the agent's allowlist. For the Developer that is anything outside `tinydb/**`, explicitly including `tests/**`, `.github/**`, `.autose/**`, `pyproject.toml`, `setup.*`, `pytest.ini`, `mypy.ini`, `uv.lock` and `ARCHITECTURE.md`; the Tester may touch only `tests/test_autose_issue_<N>.py`. The tool layer limits what the agent *tries*; this layer limits what *counts*.

**GitHub access is deterministic code only.** The orchestrator and small workflow steps use the `gh` CLI with the job's token: `git push --force-with-lease`, `gh pr create/edit`, the sticky status comment edited in place via `gh api`, `gh api .../reviews` with event `COMMENT`, labels. The fork has "Allow GitHub Actions to create and approve pull requests" enabled so `gh pr create` works with `GITHUB_TOKEN`.

### Revision note (2026-11-24, before the first run: found by an independent code review)

The first implementation leaked the write-scoped `GH_TOKEN` to agent-influenced code in three ways:

- The orchestrator process held the token while it ran `import tinydb`, `mypy` and `pytest`, all of which execute Developer- and Tester-written code.
- Unconfined file tools could read `/proc/<ppid>/environ`.
- Git hooks and config planted by agent-run code would have executed inside the orchestrator's own `git` calls.

Without a token in the process, the three layers above are not enough on their own. We therefore add a fourth rule: **no process that runs agent-influenced code ever holds a GitHub token.** This changes the implementation in five ways:

- **build/rework are split into steps.** *prepare* (token) writes the issue, trusted comments and branch facts to files. *agent* (no token) runs S1–S4 offline. *publish* (token) posts, pushes and opens the PR. The review job already had this shape.
- **`--restricted --strict-mcp-config` on every agent.** In CLI 2.1.331 this confines file tools to the working directories, ignores repo/user settings files, keeps Bash only when `--tools` names it, and denies writes to git and settings config in `-p` mode.
- **Hardened orchestrator git.** Every git call runs with `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, and check subprocesses get a scrubbed environment.
- **A final path gate before push.** `git diff --name-only --no-renames <base> HEAD` must stay within the allowlist. This also closes an index-staging bypass of the per-attempt check.
- **Workflow-command files are withheld.** `GITHUB_ENV`/`GITHUB_PATH`/`GITHUB_OUTPUT` are withheld from agents.

This refines, but does not reverse, the decision above, so we record it as a revision rather than a supersession.

## Alternatives considered

1. **GitHub MCP server for agents** (the brief's suggested option). Rich, typed GitHub operations, and agents can fetch issue context themselves. Rejected: it gives an LLM that reads untrusted text a channel to act on GitHub, and the MCP server's tool surface is far wider than any of our agents need. Nothing an agent does requires GitHub at decision time; every GitHub action is a fixed function of artifacts.
2. **`gh` CLI available to agents via Bash** (e.g. let the Release or Reviewer agent post its own review). Simple and well-known to models. Rejected for the same reason, and because a Bash prefix rule for `gh` cannot restrict *which* repo, issue or API path is called in a way we could audit.
3. **One broad permission set at workflow level** (the brief's sketch: `contents/pull-requests/issues: write` for everything). Simplest. Rejected: it would give the review job push rights, which the brief explicitly forbids, and give the gate job far more than it needs to read a collaborator's permission.
4. **Trust the tool allowlist alone, without the post-run path check.** Rejected: Bash-capable agents can write files through `python -c` or pytest side effects; the allowlist restricts commands, not their effects.

## Consequences

Positive:
- A prompt-injected agent cannot push, comment, label or open PRs: it has no token in its environment, no credential in `.git/config`, and no GitHub tool.
- The review job cannot push even if all prompt- and tool-level defences failed, because its token is `contents: read`.
- The only code that touches GitHub is ours, reviewed, and the same on every run.

Negative:
- Agents cannot look up related issues, PR history or upstream discussions that might help. For tinydb, `ARCHITECTURE.md` and `git log` (Reviewer) cover most of that need.
- Every GitHub interaction is code we write and maintain (sticky comment edit, PR upsert, review posting).

Risks:
- **Running code is running arbitrary code.** `python -m pytest` and the Reviewer's `python` probes execute repository code the Developer wrote, which was derived from an attacker-written issue. That code runs with the agent's environment, which contains `ANTHROPIC_API_KEY`, and hosted runners have unrestricted network egress. Our layers stop GitHub misuse but not exfiltration of the model key by malicious code. Mitigations: write-capable agents never see the raw issue (ADR-003), the provider-side spend limit caps damage, and keys are rotatable. A stronger fix (Claude Code's bash sandbox with an empty network allowlist, `AUTOSE_SANDBOX=1`, pending a canary) is described in ADR-009.
- Bash prefix rules are matched by the harness's parser; a compound command (`python -m pytest; curl ...`) must be split and each part checked. We rely on the harness for this and pin its version (ADR-011).

## Answers to the brief's questions

- **Which tools does each agent have?** See the table: read-only tools for Analyst and Architect; edit plus narrow Bash for Developer and Tester; read, run and scratch-write for the Reviewer.
- **How are they provided?** Built-in Claude Code tools, selected per invocation with `--tools`/`--allowedTools`. GitHub is provided to deterministic code only, through the `gh` CLI with per-job `GITHUB_TOKEN`. No MCP server.
- **How do we make sure each agent can only do what it needs?** Job permissions, a scrubbed environment and `persist-credentials: false`, per-agent tool allowlists under `--bare`, and a post-run path allowlist that fails the stage on any out-of-bounds change.

## How we will know if this is wrong

- If the ledger shows stages failing because an agent needed a denied command (e.g. the Developer needing `pip install` or the Tester needing `git diff`), the allowlists are too narrow; we widen them one prefix at a time and record each change.
- If the post-run path check fires often, agents are routinely trying to do more than their role, which points to prompt problems rather than permission problems.
- Any evidence in run logs of an agent attempting network access or reading credentials (including on the seeded injection PR in E1) means the residual risk above is real and must be closed before further runs.
