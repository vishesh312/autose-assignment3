# ADR-010: Label or `/autose` from a write-access human starts a run; one run per issue at a time

- Status: Accepted (2026-11-24)
- Decision area: D10 Triggers (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

The brief's sketch triggers on `issues: [labeled]` and `issue_comment: [created]`. Facts that shape the decision:

- **Every comment and every label fires the workflow.** `issue_comment` runs on every new comment on every issue and PR, and `issues: labeled` on every label. The workflow must filter cheaply and must not let irrelevant events disturb a real run.
- **PRs are issues to the API.** A comment on a PR arrives as `issue_comment` with `github.event.issue.pull_request` set, and `github.event.issue.number` is the **PR** number, not the issue the PR fixes.
- **`author_association` is not a permission.** `MEMBER` does not imply write access, `CONTRIBUTOR` means anyone with a merged commit, and users with only **triage** permission can add labels. Only the collaborators permission endpoint (`GET /repos/{o}/{r}/collaborators/{user}/permission`) states the real level.
- **Secrets.** `issue_comment` workflows run from the default branch with secrets even for PRs from forks (ADR-009).
- **Events from `GITHUB_TOKEN` do not start workflows**, so our own comments, labels and PRs cannot re-trigger us.
- **Actions concurrency** allows one running and one pending run per group; a newer pending run cancels the older pending one.
- Each issue maps to one branch `autose/issue-<N>` and at most one PR (ADR-004).

## Decision

### Triggers

| Event | Condition | Action |
|---|---|---|
| `issues: labeled` | label is `autose` | Full pipeline S1→S6 for that issue |
| `issue_comment: created` on an issue | body starts with `/autose` (exact command, first line) | Full pipeline; used after answering clarifying questions (`autose:needs-info`) |
| `issue_comment: created` on an AutoSE PR (`autose/issue-<N>`) | body is `/autose` | A new review round for issue N on the current head |
| `issue_comment: created` on a same-repo PR | body is `/autose review` | A review round only; the canonical issue is the one the PR body closes (`Closes #N`). Used for the 5 seeded PRs (ADR-008) |

Edited comments are ignored (`created` only), so a comment cannot be changed into a command after the fact.

### Who may start a run

The `gate` job (`issues: write`, `pull-requests: read`, `contents: read`; no secrets beyond `GITHUB_TOKEN`, no agent) checks, in order:

1. `github.event.sender.type != 'Bot'`; bot senders (other Apps) are ignored.
2. The sender's permission from the collaborators API is `admin`, `maintain` or `write`. Triage and read are rejected with a short comment. For a label this is the user who added the label, not the issue author.
3. For PR commands, the PR's head repository equals the base repository; fork PRs are rejected (ADR-009).
4. Resolves the **canonical issue number** N (the issue itself, or the issue linked from the PR) and outputs it for all later jobs.

Rejected triggers end at `gate` with no secret ever exposed to a step and no agent started.

### Two runs at the same time

- **Workflow-level:** `concurrency: { group: autose-<key>, cancel-in-progress: false }`. For trigger events (the `autose` label, or a comment starting with `/autose`) the key is `github.event.issue.number`; for every other event it is `github.run_id`, so unrelated comments and labels each get their own group, exit at `gate` in seconds, and can never cancel a queued real run. (This key expression refines DESIGN §11, which keys every event on the issue number.)
- **Job-level:** downstream jobs carry `concurrency: autose-issue-<canonical N>` from the gate's output, so an issue label (key = issue number) and a `/autose` on its PR (key = PR number) still serialise on N.
- **Effect:** a second trigger for the same issue waits until the first finishes; we never cancel in progress, because cancelling mid-push could leave a half-updated branch and PR. A third trigger replaces the queued second one (Actions behaviour), which is acceptable because all queued triggers mean "run again on the latest state". Different issues run fully in parallel: separate branches and PRs, no shared files, so they cannot conflict until a human merges one, at which point the other PR shows a normal merge conflict or needs a rebase, which is the human's call.

### Re-trigger semantics

A re-trigger starts a **fresh pipeline**: new `spec.md` from the issue thread (including answers to earlier questions), branch `autose/issue-<N>` reset to the current `main`, `git push --force-with-lease`, and the **existing** PR updated (body, trace comment, new review) instead of a second PR being opened. Round counters reset. No state is resumed from a previous run (ADR-004), so a restarted run cannot inherit a corrupted state.

## Alternatives considered

1. **Trust `author_association` (`OWNER`/`MEMBER`/`COLLABORATOR`).** One field, no API call. Rejected: it does not distinguish read, triage and write collaborators, and an org member may have no access to this repo.
2. **Trigger on `issues: opened` automatically.** Zero maintainer effort. Rejected: then the issue author, who may be anyone, starts an agent with secrets on text no human has looked at. The label is the human gate.
3. **`cancel-in-progress: true`** so the latest trigger wins. Faster feedback. Rejected: cancellation can land between push and PR update, or mid-review, leaving a branch and PR that disagree with the status comment.
4. **Workflow-level concurrency only, keyed on `github.event.issue.number`.** Simpler. Rejected because the PR number differs from the issue number, and because unrelated comments would join the group and could cancel a queued real run.
5. **Re-trigger resumes from the last good stage.** Saves tokens. Rejected (ADR-004): resuming needs trustworthy saved state across runs, and the usual reason to re-trigger (new answers, changed `main`) invalidates earlier stages anyway.

## Consequences

- **Positive.** Only people who could push code anyway can spend the API budget or start an agent. Each issue has exactly one branch, one PR and one run at a time, so every artifact on GitHub belongs to an unambiguous run.
- **Negative.** Every comment on the repo starts a short gate job (seconds of runner time). Re-triggering redoes S1–S4 even if only the review needed another look (`/autose` on the PR covers that case). A third quick trigger silently drops the second.
- **Risks.** Job-level concurrency serialises each job, not the whole chain: if run B (from the PR) and run A (from the issue) interleave, B's build could start while A's review job is still running. The post-review job therefore checks that the head SHA it reviewed is still the PR head and discards a stale review. A cleaner fix is for the gate to re-dispatch PR-originated triggers as `workflow_dispatch` with the canonical number, so workflow-level concurrency covers everything. Re-triggering resets the branch, which would overwrite commits a human pushed to `autose/issue-<N>`; the gate should refuse to reset a branch with non-bot commits. The issue author can edit the issue after a maintainer labels it; the gate should record the issue's `updated_at` and body hash in the status comment.

## Answers to the brief's questions

- **Which events start the workflow?** The `autose` label on an issue; `/autose` on an issue; `/autose` on an AutoSE PR (new review round); `/autose review` on a same-repo PR (review only).
- **Who is allowed to start it?** Humans with write, maintain or admin permission according to the collaborators API. Not bots, not triage users, not issue authors without write access, and never on fork PRs.
- **What happens if two runs start at the same time?** Same issue: the second queues behind the first, keyed on the canonical issue number, and runs fresh afterwards; a third replaces the queued one. Different issues: run in parallel on separate branches.
- **Beyond the brief.** Unrelated events cannot disturb a queued run; re-triggers update the existing PR instead of creating duplicates.

## How we will know if this is wrong

- Any Actions run where two runs for the same canonical issue overlap in their build or review jobs (visible in run timestamps in `results/runs.md`) shows the job-level serialisation is insufficient; we then adopt the `workflow_dispatch` re-dispatch.
- Any run started by a user without write access means the gate is broken.
- If maintainers find a queued trigger silently dropped in practice, we need an explicit queue (for example a label recording pending requests).
