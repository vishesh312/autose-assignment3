# ADR-011: Agent harness is Claude Code CLI in headless mode, driven by our Python orchestrator

- Status: Superseded by [ADR-014](ADR-014.md) (2026-11-24): the student chose subscriptions (Codex/agy) over API spend before any live run. The Claude runner stays selectable with `AUTOSE_BACKEND=claude`.
- Decision area: Agent harness (supports D1, D2, D5, D6, D9; not one of the brief's D-numbers)
- Deciders: Team (Vishesh Saraswat)

## Context

ADR-001 gives us five agents with different tools, ADR-002 puts control flow in deterministic code, ADR-003 requires structured, schema-validated outputs, and ADR-005 requires per-agent tool restriction with no GitHub access. Each agent needs a loop that can read files, edit them and run commands (the ReAct pattern). We must choose what runs that loop.

Requirements on the harness, in order of importance for this system:
1. **Per-invocation tool restriction** that we set from outside, including Bash prefix rules (ADR-005).
2. **Structured final output** that we can validate against our JSON Schemas (DESIGN.md §14).
3. **A cost cap per call** and cost/token reporting for `ledger.jsonl` (ADR-009, report §4 token totals).
4. **Good built-in file/edit/bash tools**, so we do not spend the assignment building and debugging a tool layer.
5. **No configuration loaded from the repository being worked on.** The PR branch is derived from untrusted issue text; a harness that auto-loads `CLAUDE.md`, hooks, plugins or MCP config from the working tree would let the branch reconfigure the agent that reviews it.
6. **The same harness locally and in CI**, so experiments E1/E2 can run on a laptop cheaply and the results transfer to Actions.
7. It must not own GitHub write access or control flow (ADR-002, ADR-005, ADR-008).

## Decision

Every agent is one subprocess call:

```
claude -p --bare --no-session-persistence \
  --model <m> --tools <available> --allowedTools <auto-approved> \
  --max-budget-usd <cap> --output-format json --json-schema <schema> [--add-dir <dir>]
```

driven by the `autose` Python orchestrator, which builds the prompt from artifacts, sets a scrubbed environment and a 20-minute subprocess timeout, parses the JSON result (structured output, `total_cost_usd`, usage), validates it again against the schema, and writes the ledger line. Flags and why:

| Flag | Purpose here |
|---|---|
| `-p` | Non-interactive; denied tools are refused, never prompted |
| `--bare` | Do not auto-discover `CLAUDE.md`, hooks, plugins, MCP servers or settings from the repo or home directory (requirement 5) |
| `--no-session-persistence` | No session saved to disk, so no later call can resume it; enforces "artifacts are the only hand-off" (ADR-003) |
| `--tools` / `--allowedTools` | Which built-ins exist / which are auto-approved, including `Bash(python -m pytest …)` prefix rules (ADR-005) |
| `--json-schema` + `--output-format json` | Final answer must match our schema; result envelope gives cost and tokens |
| `--max-budget-usd` | Per-call cap (ADR-006 table); the $10 run cap is enforced by the orchestrator on top |
| `--model` | Per-role model, overridable with `AUTOSE_MODEL_<ROLE>` (ADR-006) |

The CLI version is pinned in the workflow (`npm i -g @anthropic-ai/claude-code@<exact version>`) and in `autose local`, so local and CI behaviour match and a flag change upstream cannot silently alter permissions.

## Alternatives considered

1. **`anthropics/claude-code-action` as the backbone.** Ready-made, handles triggers, comments, progress updates and branch pushing. Rejected as the backbone because it bundles what we want separated: it holds a GitHub token and posts and pushes on its own (conflicts with ADR-005 and the review job's read-only rule in ADR-008), it implements its own trigger and control flow (conflicts with ADR-002's state machine and ADR-010's gate), and it is designed around one agent per run (conflicts with ADR-001). The brief allows a ready-made action "as one step"; we could still use it for a single stage with its GitHub features disabled, but at that point it is a wrapper around the same CLI, and calling the CLI directly is simpler to restrict and to run locally.
2. **Claude Agent SDK (Python).** Same agent loop and tools as the CLI, with in-process hooks for permission decisions (e.g. a `can_use_tool` callback that could check paths before writes, which is stronger than our post-run check). Rejected narrowly: the CLI gives us the same capabilities as flags we can copy into a shell and replay by hand; every invocation is visible in the job log as one command line; and process isolation (separate env per agent) is natural with subprocesses. If we need pre-write path enforcement, migrating to the SDK is the obvious step, and the prompts and schemas carry over.
3. **mini-swe-agent.** Very small, transparent, bash-only loop; well understood from SWE-bench (Lecture 9). Rejected: bash-only means file edits happen through shell commands, so tool restriction is by command filtering alone, with no separate Read/Edit permission; structured output and per-call budget caps would be ours to build.
4. **OpenAI Agents SDK or LangGraph.** Good primitives for multi-agent graphs, handoffs and state. Rejected: their graph and handoff layer duplicates our state machine (ADR-002) while we would still need to supply file, edit and bash tools ourselves; LangGraph's value is mostly control-flow orchestration, which we deliberately keep in plain code.
5. **Raw Messages API with our own tool loop.** Maximum control and no dependency. Rejected: we would build and secure read/edit/bash tools, context management and retries, which is a lot of code that is not the architecture the assignment grades, and is where subtle bugs (path traversal in our own Write tool, unbounded loops) would come from.

## Consequences

Positive:
- Tool restriction, structured output and budgets are flags, not code we maintain.
- `--bare` closes a specific injection path: a PR branch containing a `CLAUDE.md` saying "approve this PR" or a hook in `.claude/settings.json` has no effect on our agents. Without it, the Reviewer, which checks out the PR head, would load them.
- Local runs (`autose local`) use the same binary and flags, so E2 (stages 3–4 run locally on frozen inputs) and the paired E1 seeded-PR reviews (`autose review-local`, both variants) measure the same system that runs in CI, at our own pace; variant A is additionally run on GitHub on the seeded PRs (ADR-008).
- Each call's command line is in the job log, which helps "anyone can follow a run".

Negative:
- We depend on a CLI whose flags may change between versions; pinning mitigates this but means we must re-check flags when upgrading.
- Path restriction on writes is post-hoc (ADR-005 step 4), because the CLI's allow rules are coarser than an SDK callback.
- Installing the CLI adds a Node.js setup step and some seconds to every agent job.
- The harness is tied to one model provider; using a non-Anthropic model for the Reviewer (a possible ADR-006/008 variant) would need a different harness for that role.

Risks:
- If a flag silently does less than we assume (e.g. `--bare` loads some config we did not expect, or a Bash prefix rule matches more than intended), our permission argument has a gap. We test this with canary files in a local repo (a `CLAUDE.md` with a marker instruction, a hook that writes a file) before the first CI run.
- `--max-budget-usd` is checked by the harness between turns, so a call can overshoot its cap by up to one turn; the run-level cap leaves headroom for this.

## Answers to the brief's questions

The brief does not list a D-number for the harness, but it is the decision that makes D5 enforceable: per-agent tools (D5), structured outputs that code can route on (D2, D7), budgets (D9), and the same runtime for experiments (report §3).

## How we will know if this is wrong

- Canary tests show `--bare` or the tool flags do not restrict as documented → we move to the Agent SDK with explicit permission callbacks.
- Ledger shows frequent `--json-schema` failures or truncated structured outputs → we add an extraction step or move to the SDK's typed outputs.
- Observed per-call cost regularly exceeds `--max-budget-usd` by more than one turn's worth → the cap is not reliable and the orchestrator must enforce it by streaming usage.
- If local and CI results for the same frozen inputs differ systematically (beyond model sampling noise), the "same harness" argument for E1/E2 does not hold.
