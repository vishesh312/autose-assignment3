# ADR-012: Target tinydb @ edff96a, with deliverables in a separate submission repository

- Status: Accepted (2026-11-24)
- Decision area: Target repository and evaluation set (Part 1 of the brief; not one of the D-numbers)
- Deciders: Team (Vishesh Saraswat)

## Context

The brief asks us to fork a repository, pin a commit, and open five issues (two bugs, two small features, one vague) with two to four hidden acceptance tests each. The suggested repositories are the A2 ones (tinydb `edff96a`, mistune `f7ec702`, structlog `19c4f21`, Python-Markdown `3f2c551`) or any repo whose tests run in under five minutes. Stage 2 must use our A2 `ARCHITECTURE.md`.

Properties that matter for this architecture:
- **Suite speed.** ADR-002 runs the full suite after every Developer attempt and the Tester's fails-on-base check runs the new tests a second time on reverted files. A slow suite multiplies across up to 3 attempts × 2 designs × 3 review rounds.
- **Size.** Agents read the code through tools (ADR-003); a smaller codebase means fewer tokens per stage and a more reliable Architect.
- **Module separation.** The Architect's check (every `symbol` exists, found by AST) and the Developer's path allowlist both work best when a change maps cleanly to a few files.
- **Our own understanding.** We must write hidden tests, label seeded PRs for E1, and judge whether reviewer findings are right. That needs a codebase we know well.

A second, structural question is where the deliverables live: in the fork (which the agents work on), or in a separate repo.

## Decision

**Target: `vishesh312/tinydb`, fork of `msiemens/tinydb`, `main` cut at `edff96aeb2616402e9489d46e90a592c05565621`**, plus setup commits that add our A2 `ARCHITECTURE.md`, `.autose/` (agent code) and `.github/workflows/`. Baseline: 228 tests pass in under 1 s (pytest, Python 3.13). `main` is protected so nobody, including the bot's `GITHUB_TOKEN`, can push to it directly.

**Deliverables live in a separate submission repo, `vishesh312/autose-assignment3`.** Its `workflow/` directory is the **source of truth** for agent code, prompts, schemas and workflow YAML; `workflow/sync_to_fork.sh` copies it into the fork's `.autose/` and `.github/workflows/`. The fork contains only what the workflow needs to run. Report, ADRs, views, hidden tests, seeded-PR labels and results stay in the submission repo.

Fork setup we must do explicitly, because forks default differently: enable Issues and Actions on the fork (both are off by default for forks), store `ANTHROPIC_API_KEY` as a fork secret, allow Actions to create pull requests, and always pass `--repo vishesh312/tinydb --base main` to `gh pr create`, because in a fork `gh` otherwise defaults to the upstream parent, which the brief's "your fork only" rule forbids.

## Alternatives considered

1. **mistune `f7ec702`.** A Markdown parser with a fast suite and clear plugin structure. Rejected: we have no A2 `ARCHITECTURE.md` for it (stage 2 requires one), and parser bugs often span the block and inline layers, which makes the Architect's "name the files and functions" check harder to pass for small issues.
2. **structlog `19c4f21`.** Well-structured, good tests. Rejected: larger API surface and configuration-driven behaviour (processors, contextvars) make hidden tests harder to write without coupling them to implementation details; no A2 architecture document.
3. **Python-Markdown `3f2c551`.** Mature, many extensions, natural issue material. Rejected: a larger codebase and suite than tinydb, extensions interact through a shared registry, and again no A2 document.
4. **A repository outside the shortlist** (one we chose for interesting issues). Rejected: we would have to write a new `ARCHITECTURE.md` (which the brief says to reuse from A2), verify the "tests under 5 minutes" requirement ourselves, and lose comparability with A2.
5. **Deliverables inside the fork** (e.g. `report/`, `architecture/`, `experiment/` in tinydb's tree). One repo is simpler to submit and keeps workflow and docs together. Rejected because the agents work in the fork: the Analyst and Architect read the repo, the Reviewer checks out the PR head, and any of them could find our ADRs (which describe the reviewer's prompt strategy), the hidden tests (which would turn evaluation into a leak) and the seeded-PR labels (which would invalidate E1). It would also put our files into every diff base and into `main`, which a human maintainer would not want merged with a bug fix.

## Consequences

Positive:
- The full suite runs in about a second, so checks are dominated by model time, and re-running the suite after every attempt costs nothing meaningful.
- tinydb's modules (`database.py`, `table.py`, `queries.py`, `storages.py`, `middlewares.py`, `operations.py`, `utils.py`) map well to issue-sized changes, which suits the Architect's file-and-symbol plan and the `tinydb/**` path allowlist (ADR-005).
- We reuse A2's `ARCHITECTURE.md`, which documents the constraints (import order, all persistence through `Storage.read()/write()`) that a design is most likely to break; the Architect can cite them in `architecture_refs`.
- Hidden tests and seeded-PR labels are physically absent from anything an agent can read.
- Graders get a clean deliverable repo laid out exactly as the brief specifies, and a separate fork whose history shows only setup commits and bot branches.

Negative:
- Two repositories to keep in sync. If someone edits `.autose/` in the fork directly, the submission repo is no longer the source of truth. The sync script overwrites the fork's copies, and `runs.md` records which submission-repo commit each run used.
- tinydb is small and well-tested, so results may overstate how well this workflow would do on a larger codebase (a threat to validity for report §6).
- tinydb's suite includes upstream style/coverage configuration; an agent change that is correct but drops coverage or breaks pycodestyle will fail stage 4, which is strict but matches what upstream CI would demand.

Risks:
- Our A2 `ARCHITECTURE.md` was written for `edff96a`; if an issue requires reasoning about code it does not cover, the Architect gets no help from it. We will note which runs cited it.
- Our five issues are written by us, for a codebase we know; real users' issues would be messier. The vague issue partially tests this.

## Answers to the brief's questions

The brief has no D-number for this choice. It answers Part 1 (fork, pin, five issues, hidden tests outside the repo, protected `main`) and the submission layout, and it supports D3 and D8 by keeping evaluation material out of every agent's reach.

## How we will know if this is wrong

- If most runs stop at stage 2 or 3 because the codebase is too *trivial* to exercise loops (all issues pass first try), the evaluation does not test the architecture's routing; we would add harder issues rather than change repo.
- If agents repeatedly fail on concerns tinydb's `ARCHITECTURE.md` does not cover, the A2 document needs extending, and we record that as a finding about A2.
- If any run log shows an agent reading a path that exists only in the submission repo, separation has failed (e.g. a sync script copied too much) and must be fixed before further runs.
