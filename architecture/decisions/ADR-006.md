# ADR-006: Sonnet 5.5 for the builders, Opus 5.5 for the reviewer, Haiku 5.5 for the judge

- Status: Accepted (2026-11-24), **amended by [ADR-014](ADR-014.md)** (2026-11-24): the model table and the meaning of "cost" changed; see the revision note at the end of the Decision section. The principle (a different model for the reviewer than for the builders, per-call caps, a $10 run cap with reviewer reservation) stands.
- Decision area: D6 Models (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

ADR-001 gives us five agents (Analyst, Architect, Developer, Tester, Reviewer) and one single-shot Judge. Each runs as a separate `claude -p --bare` process (ADR-011), so the model is a per-call flag and costs nothing to vary. The forces:

- **The target is small.** tinydb @ `edff96a` (ADR-012) is about 2k LOC in `tinydb/`, the suite has 228 tests that run in under 1 s, and the five issues are small bugs and features. Work at every stage is "read a few files, change tens of lines". No stage needs a frontier model for raw capability.
- **Cost scales with the loops, not the happy path.** Up to 3 Developer attempts per design, 1 design revisit and 2 review send-backs (ADR-002, ADR-013) mean one run can make 3 reviews and several Developer calls. A choice that looks cheap on one call is multiplied by those loops.
- **Correlated errors are the main risk to the reviewer.** If the reviewer shares a model with the builders, it tends to share their blind spots: the same plausible but wrong reading of an issue, the same edge case missed. Principle 1 ("no agent grades its own homework") is weaker if the grader is the same model under a different prompt.
- **Prices** (Anthropic API list, per MTok input/output): Haiku 5.5 $0.10/$0.50; Sonnet 5.5 $2/$10 (cache reads $0.10); Opus 5.5 $4/$20 (cache reads $0.20); Fable 5.2 $8/$40. Opus 5.5 defaults to medium effort, Sonnet 5.5 to high.
- The brief requires a hard provider spend limit and a report of total tokens used.

## Decision

| Role | Model | Effort | Per-call cap (`--max-budget-usd`) | Why |
|---|---|---|---|---|
| Analyst | `claude-sonnet-5-5` | medium (lowered from Sonnet's default high) | $0.75 | Reading one issue and filling a schema; more thinking adds tokens, not quality |
| Judge | `claude-haiku-5-5` | low | $0.05 | One call, no tools, a yes/no per AC with a reason |
| Architect | `claude-sonnet-5-5` | medium | $0.75 | Read-only, bounded by an AST checker (ADR-007) |
| Developer | `claude-sonnet-5-5` | high (Sonnet default) | $1.50 | The one role where extra reasoning reduces retries; must pass mypy |
| Tester | `claude-sonnet-5-5` | medium | $1.00 | Writes one test file from the ACs |
| Reviewer | `claude-opus-5-5` | high (raised from Opus's default medium) | $2.00 | A different model from every builder, and the most capable one where an error is hardest to recover |

- **Run cap: $10** (raised from $8; see the revision note below). The orchestrator keeps a running total in `ledger.jsonl` (from the CLI's reported `total_cost_usd` per call) and refuses to start a call if `spent + that call's cap > $10`. The provider-side hard spend limit on a dedicated API key is the final backstop (ADR-009).
- **Budget reservation (refinement of DESIGN §7).** A rework (send-back) is only started if, after it, one Reviewer cap ($2) still fits under the run cap. Without this rule the estimate below shows a two-send-back run could exhaust the budget *after* rework and *before* the final review, leaving unreviewed code for the human, which ADR-013 forbids. If a rework cannot be afforded, the last review stands and the run ends `awaiting-human`.
- **Configurable.** Each model is read from a repository variable `AUTOSE_MODEL_<ROLE>` (for example `vars.AUTOSE_MODEL_REVIEWER`), with the table above as defaults. The ledger records the model of every call, so results stay attributable. If the Reviewer variable is set to the same model as any builder, the status comment carries a warning, because ADR-008 then loses one of its five independence measures. E1 variant B uses exactly this switch.

### Back-of-envelope cost per run

Assumptions (to be replaced with measured `usage` numbers after the first runs): with `--bare` and 3–6 tools the CLI's system prompt plus tool definitions is about 12k tokens; every turn re-sends the conversation, which after the first turn is a cached prefix; new tokens per turn (tool results, file reads) are about 3–4k and are billed as cache writes at about 1.25x input price; output includes thinking.

| Call | Turns | Avg cached context | Output | Est. cost |
|---|---|---|---|---|
| Analyst (Sonnet) | 8 | 25k | 10k | ~$0.18 |
| Judge (Haiku) | 1 | – (2k in) | 1k | ~$0.001 |
| Architect (Sonnet) | 12 | 35k | 12k | ~$0.28 |
| Developer, per attempt (Sonnet, high) | 25 | 45k | 25k | ~$0.61 |
| Tester (Sonnet) | 20 | 40k | 20k | ~$0.48 |
| Reviewer, per round (Opus, high) | 25 | 40k | 30k | ~$1.30 |

Worked example for the Reviewer: cache reads 25 x 40k = 1.0M x $0.20 = $0.20; cache writes 25 x 4k = 100k x $5 = $0.50; output 30k x $20 = $0.60. Output and cache writes dominate, not the cached prefix; that is why caching makes the large system prompt cheap but does not make long agent loops cheap.

- **Happy path** (one Developer attempt, approved in round 1): about **$2.85**, of which the Reviewer is ~45%.
- **One send-back to S3** (Developer + Tester + review again): +~$2.39, so about **$5.24**.
- **Two send-backs to S3**: builder rework brings the total to ~$6.33 before the final review (~$7.63 with it). The reservation rule is checked with caps: after one send-back, $5.24 + Developer $1.50 + Tester $1.00 + Reviewer $2.00 = $9.74, which fits under $10 only if spending has stayed at the estimates; one extra Developer attempt (~$0.61) anywhere in the run, or a first send-back that was `approach`, pushes it over. A second `approach` send-back (each also reruns the Architect, $0.75 cap) never fits: $5.24 + $5.25 > $10. So at $10 the first send-back of any kind is affordable after a typical run, while the second send-back that ADR-013 allows is often unaffordable; we will raise the cap further (about $11 covers two send-backs of any kind under the caps) only if the ledger shows second send-backs fixing real defects.
- **Per-call caps** bound a single runaway loop; the **run cap** binds the sum. The caps alone allow far more than $10 (3 Developer attempts x 2 designs x $1.50 is already $9, before any Tester, Architect or Reviewer call), so the run cap is the binding limit by design.

### Revision note (2026-11-24, before the first run): run cap $8 → $10

An arithmetic review of the reservation rule, not a run result, showed that at $8 the first `approach` send-back is never affordable after a typical run: $2.85 spent + Architect $0.75 + Developer $1.50 + Tester $1.00 + reserved Reviewer $2.00 = $8.10 > $8. The routing ADR-013 defines for `approach` findings would then never be exercised. At $10 the first send-back of any kind fits after a typical run; second send-backs remain often unaffordable, as documented above. Because this is a pre-run design change found by review, not something a run taught us, we revise this ADR in place rather than superseding it; DESIGN §7 and §10, the other ADRs that quote the cap (ADR-001, 002, 004, 009, 011, 013) and the views were updated to match.

### Revision note (2026-11-24, before any pipeline run): models and cost amended by ADR-014

The student decided not to use the Anthropic API and to run every agent on subscriptions instead ([ADR-014](ADR-014.md), which supersedes the harness choice in ADR-011). This is a project constraint, not a finding about the models above. The table above is kept as the record of the original decision and is still the default when `AUTOSE_BACKEND=claude`. With the default `codex` backend the defaults are:

| Role | Model | Effort | Per-call cap (notional $) |
|---|---|---|---|
| Analyst, Architect, Developer, Tester | `gpt-6.1-sol` | as in the table above | as in the table above |
| E2 Builder (variant B only) | `gpt-6.1-sol` | high | $2.50 |
| Judge | `gpt-6.1-sol` (ADR-014 first chose `gpt-6-luna`; see ADR-014's revision note) | low | $0.05 |
| Reviewer | `gpt-6-astra` | high | $2.00 |
| Verifier (ADR-015) | `gpt-6-astra` | medium | $0.50 |
| E1 friendly reviewer | `gpt-6.1-sol` (the builder model) | high | $2.00 |

What changes and what does not:

- **The reviewer is still a different model from the builders** (`gpt-6-astra` vs `gpt-6.1-sol`), but now within one vendor. Whether that is independent enough is exactly what E1's cross-vendor arm (reviewer on Claude Opus 4.6 through `agy`) checks.
- **"Cost" is notional.** A subscription has no per-call price, so each call is priced from its token counts with an assumed list-price table (`NOTIONAL_PRICES` in `workflow/autose/backends.py`). The $10 run cap, the per-call caps and the reservation rule are applied to these list-price-equivalent dollars. Tokens are reported as the real consumption. The Anthropic prices and the back-of-envelope estimates above no longer describe a default run; measured token counts replace them in `results/tokens.md`.
- **Per-call caps are checked after the call.** Codex has no `--max-budget-usd`, so a call is bounded only by its 20-minute timeout and the cap is enforced on the next call (ADR-014, Consequences). The provider-side hard spend limit becomes the subscription's own usage limit.

## Alternatives considered

1. **One model (Sonnet 5.5) everywhere.** Simplest and about $0.65 cheaper per review round. Rejected for the reviewer because the reviewer is then the same model reading the same code, which is the correlated-error case. We keep this configuration as E1 variant B so the claim is tested rather than assumed.
2. **Opus 5.5 everywhere.** Roughly doubles builder cost (to ~$3 on the happy path before review) and slows each turn, for a repo where Sonnet's capability is not the bottleneck; our failure modes are misreadings of vague text and vacuous tests, which ADR-007's checks target more cheaply than a bigger model. Rejected.
3. **Fable 5.2 for the reviewer.** At $8/$40 a review round would cost ~$2.60, larger than our per-call cap, and three rounds alone would take most of the run cap. Latency is also higher. A 2k-LOC library with a 1 s test suite does not need it. Rejected; we would revisit only if E1 shows Opus missing defects that need deeper reasoning.
4. **Haiku 5.5 for the builders.** 20x cheaper per token than Sonnet, but multi-file edits that must pass `mypy tinydb` and a fails-on-base test check reward reliability; each extra Developer attempt costs a full test cycle and a turn of the attempt budget. Rejected for builders; accepted for the Judge, whose task is a short classification with no tools.
5. **A cross-vendor reviewer** (for example an OpenAI or Google model via its own CLI). This gives the strongest error decorrelation (different training data and post-training). Rejected for now: it needs a second API key and second spend limit, a second harness whose permission and sandbox model we would have to audit against ADR-005, and a second structured-output path to keep `review.json` valid. Listed as future work; the `AUTOSE_MODEL_REVIEWER` variable is the seam where it would plug in.

## Consequences

- **Positive.** The reviewer differs from the builders in model as well as prompt and context (ADR-008). Most tokens go to Sonnet at $2/$10. The Judge costs a tenth of a cent. Every model can be swapped without a code change, which is how E1 runs.
- **Negative.** The Reviewer is ~45% of a happy-path run and up to ~$6 of a $10 run that uses all rounds. Opus at high effort is the slowest call in the pipeline, and it is on the critical path of each round. Two model families mean two sets of prompt behaviours to tune.
- **Risks.** Our token estimates are assumptions; if the real prefix or turn counts are larger, the reservation rule will end more runs at `awaiting-human`. `--max-budget-usd` is checked between turns, so one call can overshoot its cap by up to one turn (~$0.10–$0.40); the run cap is computed with the caps, not the estimates, to absorb this. Opus and Sonnet 5.5 are from the same vendor and generation, so decorrelation is partial.

## Answers to the brief's questions

- **Which model for each role, and why?** See the table. Sonnet for the four builders because the work is small and bounded by deterministic checks; Opus for the Reviewer because it is the last automated gate before a human and its context is small; Haiku for the Judge because it is a short classification.
- **Ability.** Spent where an error is least recoverable: the Reviewer (errors reach the human) and the Developer's effort level (errors cost a full retry).
- **Cost.** Estimated ~$2.85 per happy-path run, capped at $10 per run, per-call caps per role, provider hard limit. The reviewer's premium is bounded because its context is the issue, the diff and the files it opens, not the whole pipeline history (ADR-003).
- **Speed.** The builder loop dominates wall-clock time; we keep it on Sonnet and lower effort where thinking does not pay (Analyst, Architect, Tester).
- **Value of different models.** Decorrelation: a second model is less likely to share the builder's misreading. This is a hypothesis, measured in E1.
- **Beyond the brief.** Effort is tuned per role, not only the model; a reservation rule protects the final review from budget exhaustion; tokens and cost are logged per call for the report.

## How we will know if this is wrong

- **E1** (ADR-008): if variant B (Sonnet reviewer with full context) has the same false-approval count and finding accuracy on the 5 seeded PRs and real PRs as variant A, the Opus premium is not buying anything and we supersede this ADR with a single-model setup.
- If ledger data show the Developer averaging more than 2 attempts per issue, Sonnet (or its effort level) is too weak for the Developer role and we test Opus there.
- If measured per-call costs differ from the table by more than 2x, or more than one run in five ends on the reservation rule, we revise the caps.
- If the Judge's testability verdicts disagree with the Tester's ability to write a failing-on-base test for an AC more than occasionally, Haiku is too weak for the Judge.
