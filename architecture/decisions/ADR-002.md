# ADR-002: A deterministic state machine inside jobs, a fixed unrolled job DAG across them

- Status: Accepted (2026-11-24)
- Decision area: D2 Control flow (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

The workflow has loops: tests fail and go back to implementation; repeated failure goes back to design; the reviewer sends work back to stage 2, 3 or 4 at most twice. These loops have to run inside GitHub Actions, which imposes hard constraints:

- **Jobs form a DAG.** `needs:` cannot express a cycle, so a review round cannot "jump back" to the build job.
- **Events created with `GITHUB_TOKEN` do not start new workflow runs** (except `workflow_dispatch` and `repository_dispatch`). A design where the build job opens a PR and a `pull_request`-triggered review workflow picks it up does not work without a PAT or a GitHub App token.
- Jobs on hosted runners start from a fresh VM; state does not flow between jobs unless we move it (ADR-004).
- Permissions are set per job, and the brief requires the reviewer to have no push rights. So build and review cannot share a job.

Inside a stage, deciding "pass, retry, go back or stop" is a function of check results and counters. LLMs are good at producing artifacts and bad at keeping count of retries, honouring budgets, or refusing to loop.

## Decision

Two levels of control, both deterministic (DESIGN.md principle 2: *LLMs produce artifacts, code decides transitions*).

**Inside a job: the `autose` Python state machine.** Each stage is `run_agent → validate schema → run check predicates → route`. The transition function is `next_stage = f(stage, check_result, counters)`, with counters held in `state.json` and every transition appended to `ledger.jsonl` (`stage`, `attempt`, `actor`, `model`, `event`, `passed`, `reason`, `tokens_in`, `tokens_out`, `cache_read`, `cache_write`, `cost_usd`, `seconds`; DESIGN §14). Routing rules:

| From | Condition | To |
|---|---|---|
| S1 | blocking open question | stop, label `autose:needs-info` |
| S1 | schema/structure invalid or Judge rejects an AC | S1 once with reasons, then stop |
| S2 | checker fails | S2 once with message, then stop |
| S3 | build check fails | S3 (counts as an attempt) |
| S4 | Tester's own check fails (non-test path, AC without a test, collection error, no new test fails on base) | S4 once with checker output (2 Tester attempts per design), then stop |
| S4 | suite or new tests fail | S3, at most 3 Developer attempts per design |
| S4 | 3 attempts used | S2 once with `failure_summary.md`, then stop |
| S3/S4 | same diff hash or same failing set as last attempt | escalate immediately (no-progress detector) |
| S6 | any **blocking** `approach` finding | S2 → S3 → S4 → S5 → S6 |
| S6 | else any blocking `code` finding | S3 → … → S6 |
| S6 | else any blocking `tests` finding | S4 → S5 → S6 |
| S6 | approve, or 2 send-backs used | finalize, human decides |

**Across jobs: a fixed DAG unrolled to the maximum number of rounds.**

```
gate ─▶ build(S1→S5) ─▶ round1[ci ─▶ review ─▶ post] ─▶ round2[rework ─▶ ci ─▶ review ─▶ post] ─▶ round3[...] ─▶ finalize
```

`round2` and `round3` call the reusable workflow `autose-round.yml` with `if:` on the previous round's `verdict` output, so a loop of at most two send-backs becomes three straight-line rounds of which the unused ones are skipped. `rework` runs the same state machine starting from the stage the reviewer routed to. CI is called as a reusable workflow (not triggered by the push), which sidesteps the `GITHUB_TOKEN` trigger rule.

**Who decides to go back?** Always the orchestrator. Agents only *report*: the Tester reports failing tests, the Developer can contest a test, the Reviewer classifies each finding as `approach`/`code`/`tests` and as `blocking`/`minor`; only blocking findings route (ADR-008, ADR-013). The orchestrator turns those structured fields into a route using the table above. The Reviewer's categories influence the route; they do not choose it, and they cannot exceed the round limit.

## Alternatives considered

1. **LLM planner / orchestrator-worker** (a supervising agent decides the next stage). Flexible, and can handle unforeseen situations, e.g. deciding that a test failure is really a spec problem. Rejected: retry limits and budget become prompt suggestions rather than invariants; behaviour differs run to run, which makes our per-stage pass rates (report §4) hard to interpret; and it puts a decision-making LLM in the path of untrusted text. The fixed six stages in the brief already give us the plan, so a planner would mostly re-derive it.
2. **Separate workflows that trigger each other** (build opens PR → `pull_request` triggers review → review comment triggers rework). Natural "event-driven" shape. Rejected: events from `GITHUB_TOKEN` do not start workflows, so this needs a PAT or App token with broad scope in the repo, which is a larger secret to protect; the run is then spread over several Actions runs and harder to follow; and it opens loop risks (a bot comment re-triggering the bot) that we would have to guard against separately.
3. **One job running everything, including review.** Simplest, and state never leaves the runner. Rejected: the reviewer would share a runner, filesystem and token with the job that pushed, which breaks the brief's "no permission to push" and our independence argument (ADR-008).
4. **`workflow_dispatch` self-re-dispatch for rounds** (each round dispatches the next run). This is allowed with `GITHUB_TOKEN` and gives true loops. Rejected for now: it splits one issue's history across runs and needs `actions: write`. It is our fallback if the unrolled DAG turns out to be too rigid.

## Consequences

Positive:
- Loop bounds, budgets and stop conditions are code and are unit-testable without a model (`autose local` runs the same state machine on a laptop).
- One Actions run per trigger: a reader follows gate → build → rounds → finalize on one page, which serves the brief's "anyone can follow a run".
- Clear blame: every stop has a ledger line naming the failed predicate.

Negative:
- The DAG must be unrolled; changing the round limit means editing YAML, not a constant.
- Skipped round jobs still appear in the run graph, which is slightly noisy.
- The routing table cannot handle a case we did not anticipate, e.g. a reviewer finding that the *spec* is wrong. Such findings are classified as `approach` and go to design, which may be the wrong place.

Risks:
- A long run (three rounds, each with up to several Developer attempts) is bounded by job timeouts (build 60 min, review 45, CI 15) and the $10 cap (ADR-009), but a run that hits a timeout mid-stage stops with less information than a run that fails a check.

## Answers to the brief's questions

- **How is the workflow controlled?** A deterministic state machine (Python) inside each job, plus a fixed, unrolled DAG of Actions jobs with reusable round workflows. Not an LLM planner and not workflows triggering each other.
- **Who decides when to go back?** The orchestrator, using structured fields from agents (test results, contested tests, reviewer finding categories) and its own counters. No agent can force a transition or extend a limit.
- **Beyond the brief:** the no-progress detector stops loops where retrying would not help; the design revisit (S4 → S2) exists because the brief notes that repeated test failure may mean the design is wrong.

## How we will know if this is wrong

- If the ledger shows many stops caused by routing mistakes, e.g. reviewer `code` findings that were really design problems and keep failing after rework, the fixed routing is too coarse and we would let a constrained LLM call propose the route (still validated by code).
- If unrolled rounds cause frequent Actions problems (job-level timeouts, too many skipped jobs, re-runs that misbehave), we supersede the cross-job part with `workflow_dispatch` self-re-dispatch.
- If the no-progress detector fires on runs that the next attempt would have fixed (visible in local replays with the detector off), it is too aggressive.
