# ADR-003: Hand-offs are schema-validated artifacts only; each agent gets a curated subset

- Status: Accepted (2026-11-24)
- Decision area: D3 Hand-offs (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

Five agents (ADR-001) pass work along a pipeline with loops (ADR-002). What each agent receives decides three things at once:

- **Quality.** Too little context and the Developer cannot implement the right thing; too much and it drowns, or anchors on irrelevant reasoning.
- **Independence.** The Tester and the Reviewer are only useful if they do not inherit the beliefs of the agent they check. If the Tester reads "I handled the empty-list case by returning `[]`" in the Developer's notes, it will write a test for exactly that, right or wrong.
- **Safety.** The issue body is attacker-controlled. Every place it is passed verbatim is a place where an injection can act (DESIGN.md principle 6).

Our harness (ADR-011) runs each agent with `--no-session-persistence`, so nothing is carried over implicitly between calls; whatever an agent knows, we gave it on purpose. Agents return a final JSON object under `--json-schema`, which the orchestrator validates again and renders to Markdown (DESIGN.md §14).

## Decision

**Artifacts are the only hand-off** (principle 4). No transcripts, chains of thought or free-form "notes to the next agent" cross between agents; only fields defined in a schema do. Each agent gets a curated subset:

| Agent | Receives | Deliberately excluded | Why excluded |
|---|---|---|---|
| Analyst | Issue title/body, comments from write-access users (Q&A), fenced as untrusted; read-only repo; A1 skill | `ARCHITECTURE.md`, other issues/PRs, comments from non-collaborators | Spec should describe *what*, not be shaped by *how*; outsiders' comments are an injection channel |
| Judge | Only the AC list from `spec.json` | Everything else | An AC that is only testable given extra context is not testable as written |
| Architect | `spec.md`, `ARCHITECTURE.md`, read-only repo; on loop-back `failure_summary.md` or reviewer `approach` findings | Raw issue, Analyst transcript | Raw issue is untrusted; spec is the contract |
| Developer | `design.md`, `spec.md`, repo (write within allowlist); on retry failing test ids + assertion output (≤4 KB) or reviewer `code` findings | Raw issue, Tester reasoning, earlier Developer transcripts | Fresh context per attempt; only facts about the last failure carry over |
| Tester | ACs from `spec.md`, the `public_api`/test-hooks section of `design.md`, repo incl. implementation | `dev_notes.json`, Developer transcript, rest of `design.md` | Tests derive from the spec, not from what the implementer believes it did |
| Reviewer | Raw issue (fenced), `git diff base...head`, repo at PR head, its **own** previous findings | `spec.md`, `design.md`, `test_report.md`, `pr.md`, all transcripts, GitHub access | Reviewer forms expectations from the issue itself, so an error introduced by the spec is visible to it (ADR-008) |

Further rules:
- **Structured fields for anything that routes.** Failing tests, contested tests, reviewer finding categories and AC→change/AC→test mappings are schema fields, because the orchestrator acts on them (ADR-002). Prose (`*_md` fields) is for humans and for the next agent's understanding, never for control.
- **Facts, not opinions, on retry.** A retrying Developer gets test ids and truncated assertion output, not the Tester's explanation of what went wrong.
- **Untrusted text is fenced.** Wherever raw issue text appears it is wrapped in a delimited block labelled as data, with an instruction that it may contain instructions that must not be followed (ADR-009).
- **Repo access is a tool, not a payload.** We do not paste source files into prompts; agents read what they need with Read/Grep/Glob. This keeps prompts small and lets the agent decide relevance, at the cost of more tool calls.

## Alternatives considered

1. **Shared conversation / full transcript forwarding** (each agent sees everything before it). Maximum information, and what a single long-running agent effectively has. Rejected: it destroys the independence that justifies the split (ADR-001), carries the raw issue into every write-capable agent, and grows the context with every stage. Long contexts of earlier reasoning also make later agents anchor on it.
2. **LLM-written summaries between stages** ("summarise what the next agent needs to know"). Compact and flexible. Rejected: the summariser decides what the next agent sees, so errors and injected content can be smuggled through a free-text channel that no code checks, and omissions are silent. Our schema fields do the same job with a fixed, auditable shape.
3. **Give every agent all artifacts but no transcripts.** Simpler to wire, and still free of chain-of-thought. Rejected for the Tester and Reviewer specifically: `dev_notes.json` and `design.md` are exactly the implementer-side beliefs these two roles exist to check. For the Developer it would mean little change, which is why the Developer already gets both spec and design.

## Consequences

Positive:
- Each hand-off is a file that can be shown in the trace comment and inspected; the brief's "anyone can follow a run" falls out of this.
- Raw issue text reaches only two read-only agents (Analyst, Reviewer).
- Schemas make hand-offs testable: we can replay any stage locally from saved artifacts (useful for E2, which freezes `spec.md`/`design.md`).

Negative:
- Information is lost by design. If the Analyst misreads the issue, the Architect, Developer and Tester cannot notice, because none of them see the issue. Only the Reviewer can catch it, late, and fixing it costs a full send-back.
- The Tester, without design rationale, may write tests for behaviour the design explicitly decided against; this surfaces as contested tests.
- Schemas need maintenance: every new piece of information that must cross a boundary is a schema change in `workflow/autose/schemas/`.

Risks:
- The Tester still reads the implementation through the repo. Exclusion of `dev_notes.json` does not stop it from inferring the Developer's intent from the code (see ADR-001 Risks).
- The 4 KB truncation of failure output may cut off the useful part of a traceback; we keep the tail rather than the head for that reason.

## Answers to the brief's questions

- **What does each agent receive?** Full artifacts (not summaries) for the parts it needs, plus read access to the repository through tools; see the table.
- **What is left out, and why?** Transcripts for everyone (independence, context size); raw issue for write-capable agents (safety); implementer notes and design for the Tester and Reviewer (independence); `ARCHITECTURE.md` for the Analyst (keep spec solution-free).
- **Beyond the brief:** routing-relevant information is always a schema field, retries carry facts rather than opinions, and the Reviewer's memory across rounds is limited to its own previous findings, so it can check whether they were fixed without seeing how.

## How we will know if this is wrong

- If many runs reach review with a finding that the spec misread the issue, the Analyst→everyone-else boundary is too lossy; we would give the Architect the fenced issue as well.
- If contested tests are frequent and most are resolved in the Developer's favour, the Tester needs more of the design (e.g. `approach` and `risks`).
- **E1** gives the "friendly" reviewer variant the full artifact set. If it is *not* worse on false approvals of seeded defects, excluding artifacts from the Reviewer is not buying independence and only costs it context.
