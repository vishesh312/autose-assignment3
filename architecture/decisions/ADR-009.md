# ADR-009: Layered limits for cost and time, and layered defences against prompt injection, with the residual risk stated

- Status: Accepted (2026-11-24). The credential and sandbox parts of the residual-risk analysis are updated by [ADR-014](ADR-014.md) (Codex sandbox blocks network for agent commands; the CI credential is a ChatGPT `auth.json`, not a spend-capped API key).
- Decision area: D9 Safety and failures (from the brief)
- Deciders: Team (Vishesh Saraswat)

## Context

The workflow runs LLM agents with write access to a working tree, on a public repository where anyone can open an issue, inside GitHub Actions. The forces:

- **Runaway cost.** The S3↔S4 loop, a design revisit and two review send-backs (ADR-002, ADR-013) can multiply calls. One agent can also loop on its own inside a single call.
- **Stuck stages.** An agent can repeat the same wrong fix; a subprocess can hang; a job can hit its time limit and die without explaining why.
- **Actions realities.** Events created with `GITHUB_TOKEN` (push, PR opened) do **not** trigger other workflows, except `workflow_dispatch` and `repository_dispatch`, so the fork's normal `push`/`pull_request` CI would never run on a bot PR. Jobs have time limits. A concurrency group holds at most one running and **one pending** run; a newer pending run cancels the older pending one.
- **Untrusted text.** Issue bodies, issue comments, PR descriptions and code in the PR branch are attacker-influenced. `issue_comment` workflows run from the default branch **with secrets**, even when the comment is on a PR from a fork; only `pull_request` from forks is secret-free. That is the "pwn request" pattern.
- **Agents run code.** The Developer, Tester and Reviewer run `pytest` on agent-written code. That code runs with whatever is in the process environment, which must include `ANTHROPIC_API_KEY` for the CLI to work.

## Decision

### Budgets, attempts and time

| Limit | Value | Enforced by |
|---|---|---|
| Per call | `--max-budget-usd` per role ($0.05–$2.00, ADR-006) | Claude Code CLI |
| Per run | $10, with one reviewer cap reserved before any rework (ADR-006) | Orchestrator, from `ledger.jsonl`, before each call |
| Provider | Hard monthly spend limit on a dedicated API key used only by this workflow | Anthropic console |
| Attempts | 2 spec, 2 design, 3 Developer and 2 Tester per design, 1 design revisit, 2 review send-backs | `state.json` counters, orchestrator |
| Agent subprocess | 20 min wall clock, then killed | Orchestrator (`subprocess` timeout) |
| Jobs | `timeout-minutes`: build/rework 60, review 45, ci 15 | Actions |
| Stuck | Same diff hash **or** same failing-test set as the previous attempt: escalate at once (to S2 if a revisit is left, else stop) | Orchestrator |

Because one build job can contain many 20-minute subprocesses, the orchestrator also keeps a job-level deadline: it does not start a new agent call if the job's remaining time is less than the per-call timeout (20 min) plus 2 min, i.e. 22 min, and stops cleanly instead. The review job's 45 min leaves room for an invalid-review re-ask after a first Reviewer call of up to about 20 min. The `finalize` job runs under `if: always()`, so even a job killed by Actions leaves a status comment and an `autose:failed` label. Every stop writes `## Stop reason` into the failing stage's artifact (brief: "explain why in its artifact and stop").

### GitHub Actions limits

- **CI on bot PRs.** CI is a reusable workflow called by the round (`uses: ./.github/workflows/autose-ci.yml`) on the head SHA; the `ci` job (`contents: read`, `statuses: write`) posts a commit status, so the result is visible on the PR. We do not use a PAT or GitHub App token to get "real" triggers: that would put a long-lived credential with broader scope into the workflow.
- **Concurrency.** One run per issue at a time, at most one queued (ADR-010).
- **Rate limits.** Only deterministic code calls GitHub; it makes a few dozen calls per run, far below the `GITHUB_TOKEN` limit of 1,000 requests per hour per repository.
- **Artifact retention.** Workflow artifacts expire (90 days by default); the durable record is on the issue and PR (ADR-004).

### Prompt injection: defences in layers

No single layer is trusted; each one assumes the others failed.

1. **Human gate** (ADR-010). Only users with write/maintain/admin permission (collaborators API) can start a run; a maintainer reads the issue before labelling it. Bot senders are ignored. `/autose review` on a PR from a fork is rejected, because `issue_comment` would run fork code with secrets.
2. **Data fencing.** Untrusted text is passed inside delimiters with a per-run random nonce and labelled as data, so it cannot close its own fence. Only comments from write-access users are included. The Analyst records suspicious text in `spec.json.injection_findings`; the Reviewer in `injection_attempts_noticed`. Both appear in the posted artifacts.
3. **Containment of untrusted text** (principle 6). Only the Analyst (read-only) and the Reviewer (read-only, no push) read the raw issue. Write-capable agents see only `spec.md`/`design.md` derived from it (ADR-003).
4. **No exfiltration tools.** No agent has WebFetch, WebSearch, MCP or a GitHub token; Bash is limited by `--allowedTools` patterns (ADR-005).
5. **`--bare`.** The CLI does not load `CLAUDE.md`, hooks, plugins or MCP config from the checkout, which is attacker-influenced on a PR branch. A malicious `.claude/settings.json` or hook in the branch is never executed by the harness.
6. **Deterministic path allowlists after every agent.** Developer: `tinydb/**` only, so any other path fails the stage, explicitly including `tests/**`, `.github/**`, `.autose/**`, `pyproject.toml`, `setup.*`, `pytest.ini`, `mypy.ini`, `uv.lock` and `ARCHITECTURE.md`; Tester: only `tests/test_autose_issue_<N>.py`; Architect's plan: `tinydb/**` only. An injection therefore cannot change CI, the orchestrator or test configuration.
7. **Independent reviewer reads the raw issue**, so an injection that steered the spec can be caught by comparing the PR to the original text; seeded PR (v) tests this (ADR-008).
8. **Branch protection and human merge.** `main` cannot be pushed to; nothing is merged without a person (ADR-013).

### Residual risk (stated, not solved)

When an agent runs `pytest`, agent-written code executes in a process whose environment includes `ANTHROPIC_API_KEY`. An injection that survives layers 1–3 could produce code that reads the key and sends it out over the network; tool restrictions do not stop code that pytest runs. In the build job the same code could also tamper with files outside the repository (for example under `$HOME` or site-packages) that the later deterministic Release step relies on; our allowlists check the repository tree only. Mitigations: the key is dedicated, spend-capped and revocable; runners are ephemeral; the orchestrator runs from a copy outside the agent's working tree; `GITHUB_TOKEN` is never in an agent's environment and `persist-credentials: false` keeps it out of `.git/config`. With `AUTOSE_SANDBOX=1`, Claude Code's bash sandbox (bubblewrap on Linux) wraps the agents' Bash commands with an empty network allowlist (`sandbox.network.allowedDomains=[]`) and `ANTHROPIC_API_KEY` denied to sandboxed commands (`credentials.envVars`), so code run by pytest neither sees the key nor reaches the network; this mitigation is **pending a canary run on `ubuntu-latest`** (DESIGN §10.1), we do not rely on it until the canary passes, and the result will be recorded here. Planned hardening: `step-security/harden-runner` with an egress allowlist (`api.anthropic.com`, `github.com`, `pypi.org`) in block mode. A stronger fix, moving Release into its own job on a clean runner, is future work.

## Alternatives considered

1. **Trust any trigger, rely on the model to ignore injected instructions.** Rejected: prompt-level defence alone is known to be bypassable, and a write-capable agent with secrets is the worst place to test that.
2. **Sanitise or classify the issue with an LLM before use.** Rejected as a primary defence: the classifier is itself injectable and adds a call. The Analyst's `injection_findings` serve as a signal for the human, not a gate.
3. **A PAT or GitHub App token so bot PRs trigger normal CI.** Rejected: a long-lived, broader credential in the workflow for a convenience the reusable workflow provides.
4. **Only a run-level budget, no per-call caps.** Rejected: one looping agent could spend the whole run budget on one call before the orchestrator regains control.

## Consequences

- **Positive.** Cost per run has a known ceiling ($10, exceeded by at most one turn's overshoot of the last call) and a provider backstop. Every failure ends with a written reason on GitHub. An injection must defeat a human gate, fencing, containment, tool limits and path allowlists, then a reviewer and a human, before reaching `main`.
- **Negative.** The limits end some runs that would have succeeded with one more attempt. The reusable-workflow CI is ours, not the fork's own CI, so it must be kept in step with upstream. Each layer is code to maintain and test.
- **Risks.** The residual risk above. `--max-budget-usd` is checked between turns, so a call can overshoot by one turn. A third trigger on the same issue silently cancels the queued second one (ADR-010).

## Answers to the brief's questions

- **Budgets:** per call, per run with a reserved review, provider hard limit, attempt counters. **Timeouts:** per subprocess, per job, plus a job-level deadline in the orchestrator. **Actions limits:** reusable-workflow CI with a commit status, job timeouts, concurrency queue of one, low API use. **Stuck stages:** no-progress detector on diff hash and failing set, escalating to S2 or stopping.
- **Prompt injection, given anyone can write an issue:** eight layers above; the strongest are that a human with write access must choose to run the bot, and that untrusted text only reaches read-only agents.
- **Beyond the brief:** fork-PR rejection for the `issue_comment` pwn-request case; `--bare` against branch-controlled harness config; an honest statement of the risk we have not closed.

## How we will know if this is wrong

- If any run ends because a job timed out rather than with a written stop reason, the deadline logic is insufficient.
- If the no-progress detector fires on attempts that later would have passed (visible when a re-trigger succeeds), it is too eager.
- If seeded PR (v)'s injection reaches a verdict of `approve`, or any agent output touches a forbidden path and is caught only by the allowlist, we add a layer (for example harden-runner in block mode by default).
- If the sandbox canary shows a sandboxed command can read `ANTHROPIC_API_KEY` or reach the network, `AUTOSE_SANDBOX=1` is not a mitigation on our runners and we fall back to harden-runner and the residual-risk statement above.
- If harden-runner's audit log shows egress to hosts outside the allowlist during agent steps, the residual risk is real and must be closed before the bot is used on issues from outsiders.
